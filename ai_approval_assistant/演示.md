两者的核心区别是：一个由 Workflow 控制执行顺序，一个由 Agent 自己决定调用什么工具。
## `daily_report_create_agent` 怎么执行

daily_report_create_agent大致是这样的：
```text
用户消息
   ↓
create_agent / ReAct Agent
   ↓
模型自己判断下一步
   ↓
选择并调用日报工具
   ↓
观察工具结果
   ↓
继续调用工具或回答用户
```

例如模型可能自主决定：

```text
get_current_daily_report_date
    ↓
load_daily_report_context
    ↓
save_daily_report_draft
    ↓
preview_daily_report_payload
```
- 快速验证自主 Agent。
- 工具调用实验。
- 流程不严格的智能助手。
- 希望 Agent 自己决定处理步骤的场景。

## `daily_report_agentic_workflow_demo_node` 好在哪里

它在顶层看起来只是一个节点：

```text
daily_report_agentic_workflow_demo_node
```

但进入这个节点后，内部会展开为一个子图：

```text
demo_agent_plan
        ↓
demo_confirm_date
        ↓
demo_load_context
        ↓
demo_agent_compose
        ↓
demo_save_draft
        ↓
demo_preview_gate
        ↓
等待用户确认
        ↓
demo_submit_gate
```

这里采用的是：

> Agent 负责智能判断，Workflow 负责业务规则。

### 1. 强制保证执行顺序

Workflow 可以从代码层面保证：

```text
确认日期
  ↓
加载上下文
  ↓
生成内容
  ↓
保存草稿
  ↓
展示预览
  ↓
确认提交
```

Agent 即使建议直接提交，Workflow 也可以拒绝。 所以它不是依赖 Prompt 说“请不要直接提交”，而是代码直接限制不能提交。 这是它最重要的优势。

### 2. Agent 权限更小、更安全

在 `daily_report_create_agent` 中，Agent 可以自主选择所有注册给它的工具。

而 Agentic Workflow 可以把职责拆开：

```text
Agent 节点：
- 理解用户输入
- 提取日期和工作内容
- 生成日报正文
- 给出下一步建议

Workflow 节点：
- 调用 ERP 接口
- 保存草稿
- 生成预览
- 检查确认状态
- 执行最终提交
```

### 3. 更容易排查问题

`daily_report_create_agent` 出现问题时，通常需要查看：

- Agent 消息历史。
- 模型返回的 tool calls。
- 工具调用参数。
- 工具调用顺序。
- 模型为什么没有继续调用工具。

而 Agentic Workflow 的 `trace` 会明确显示：

```json
[
  "daily_report_agentic_workflow_demo",
  "demo_agent_plan",
  "demo_confirm_date",
  "demo_load_context",
  "demo_agent_compose",
  "demo_save_draft",
  "demo_preview_gate"
]
```

如果没有生成日报内容，可以直接查看：

```text
demo_agent_compose
```

如果没有进入预览，可以查看：

```text
demo_save_draft
demo_preview_gate
```

如果确认后没有提交，可以查看：

```text
demo_submit_gate
```

因此排查问题时，不需要猜“Agent 当时为什么没有调用某个工具”。

### 4. 状态更加清晰

Agentic Workflow 会把中间结果分别保存到状态中：

```json
{
  "daily_report_agentic_plan": {},
  "daily_report_agentic_context": {},
  "daily_report_agentic_compose": {},
  "daily_report_agentic_demo_events": [],
  "daily_report_agentic_draft_saved": true
}
```

可以明确知道：

- Agent 理解出了什么计划。
- 加载了哪些上下文。
- Agent 最终生成了什么内容。
- 草稿是否已经保存。
- 当前停在什么业务阶段。

`create_agent` 的状态则更多保存在：

```json
{
  "daily_report_agent_messages": []
}
```

需要从消息和工具调用历史中反推当前业务阶段，前端和后端都更难处理。

### 5. 更容易写稳定测试

Agentic Workflow 可以分别测试：

```text
日期确认节点
上下文加载节点
正文生成节点
草稿保存节点
预览节点
提交 Gate
```

例如可以明确测试：

```text
没有预览时不能提交
用户没有明确确认时不能提交
日报内容为空时不能保存
日期没有确认时不能加载上下文
```

而测试 `create_agent` 时，通常要模拟完整的模型响应、工具调用和消息序列。模型调用顺序发生变化，测试就可能失败，即使最终业务结果没有错误。

### 6. Token 和调用次数更加可控

`create_agent` 可能出现循环：

```text
模型思考
→ 调工具
→ 模型观察
→ 再调工具
→ 再观察
→ 再决定
```

每次工具调用后都可能再次调用模型，因此 Token、延迟和成本不容易完全预测。

Workflow 的路径通常是固定的：

```text
计划一次
生成一次
其他步骤由普通代码执行
```

所以更容易控制：

- 模型调用次数。
- 接口调用次数。
- 总处理时间。
- Token 成本。
- 最大重试次数。
