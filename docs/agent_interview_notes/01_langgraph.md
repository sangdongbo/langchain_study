## 1. 一句话定位与技术边界

LangGraph 是面向有状态、可循环、可暂停恢复任务的低层编排框架与运行时。它把确定性代码和模型决策放进同一执行图，明确状态如何传递、下一步如何选择、失败后从哪里继续。

面试不要只说“用来画流程图”。真正价值是让多步任务拥有可检查的执行语义：状态更新、分支、并发、检查点、中断、恢复和流式事件。

| 技术 | 主要解决什么 | 不自动解决什么 |
| --- | --- | --- |
| 普通 Python 函数 / 脚本 | 固定顺序、局部控制流 | 长任务恢复、跨请求状态管理 |
| LangChain | 模型、工具、消息、Agent 循环及集成 | 任意业务流程的全部架构设计 |
| LangGraph | 有状态编排与运行时控制 | 模型质量、业务权限、外部系统事务 |
| Deep Agents | 在 LangGraph 等基础上组装 Agent harness | 自动保证业务结论正确 |
| LangSmith | 追踪、评估等开发运维能力 | 替代图本身的控制逻辑与检查点 |

LangGraph 不要求每个节点都调用 LLM，也不要求必须依赖 LangChain 的模型封装。规则、检索、校验、人工决策、模型调用都可以成为节点。

适用：多轮工具调用、复杂审批、需要恢复的研究任务、带验证闭环的业务 Agent。
不必使用：一次格式转换、一个固定 HTTP 调用、几步简单且可重跑的小脚本。

## 2. 核心概念：先分清对象再谈设计

| 概念 | 含义 | 设计时的问题 |
| --- | --- | --- |
| State | 图当前的共享业务状态 | 哪些事实需要被后续步骤看到？ |
| Node | 读取状态并产生更新的函数 / Runnable | 是否承担过多职责或副作用？ |
| Edge | 下一步执行关系 | 固定顺序还是条件路由？ |
| Reducer | 某个状态字段如何合并更新 | 覆盖、追加、去重还是版本冲突？ |
| `START` / `END` | 图入口与结束标记 | 什么条件才算结束？ |
| Compile | 将图定义变成可执行对象 | 是否配置检查点、Store 等运行能力？ |
| Thread | 一条持久化执行历史的逻辑容器 | 谁拥有它，能否跨用户访问？ |
| Checkpoint | 执行状态快照与恢复信息 | 能恢复到哪个边界？ |
| Runtime context | 本次调用注入的上下文 | 身份、客户端、配置从哪里可信地取得？ |

不要把 `thread_id`、用户 ID、租户 ID、业务申请 ID 当作同一个概念。它们可以有关联，但用途不同：thread 定位执行历史，认证身份决定访问权限，业务 ID 标识业务对象。

## 3. State：不是普通全局字典

### 3.1 Schema、更新与校验

常见状态声明方式：

- `TypedDict`：表达字段与静态类型，运行开销小；普通 Python 不会因此自动严格校验所有输入。
- `dataclass`：便于声明默认值和数据对象。
- Pydantic：适合需要递归输入校验的场景，但不要据此假定每次节点写入、字段修改、最终输出都自动满足业务不变量。

节点通常返回部分更新，而不是把整个状态原样返回。每个字段独立应用 reducer。

状态字段应优先保存可序列化业务事实、来源、阶段和操作 ID。不要把数据库连接、浏览器 Page、打开的文件句柄或密钥直接塞进持久化 State；它们应由运行环境重新提供。

### 3.2 默认覆盖与自定义合并

没有显式 reducer 的普通字段，更新通常覆盖旧值。两个并行节点在同一 super-step 写同一个单值字段，可能产生并发更新错误，不能假设“最后完成的覆盖前面”是可靠业务策略。

`Annotated[list, operator.add]` 表示列表拼接，不代表去重，也不保证拼接顺序就是业务排序。并行结果最好带稳定 ID，在汇总节点显式排序、去重和处理冲突。

### 3.3 `messages` 与 `add_messages`

消息列表需要维护消息 ID、类型和 tool-call / tool-result 对应关系。`add_messages` 不只是列表加法：它可按消息 ID 更新已有消息，适合消息状态管理。

`MessagesState` 提供常用的消息状态定义。不要把它理解成“无限保存所有对话就是记忆管理”。历史仍需裁剪、摘要和隐私控制。

### 3.4 状态、上下文、Store 的边界

- State：当前任务进行到哪一步、收集了哪些证据。
- Runtime context：可信调用方传入的租户、角色、客户端、功能开关等。
- Store：跨 thread 的持久化资料或记忆，需要命名空间和访问控制。
- Prompt：发送给模型的输入视图，不应该等同于以上所有数据的全集。

## 4. 图如何执行：super-step 与屏障

LangGraph 的图执行借鉴 Pregel 消息传递思想，以离散 super-step 推进。当前步中被激活的节点可以并行执行，更新在步边界合并，再影响下一步。

理解这个机制能解释三个现象：

1. 并行兄弟节点不应指望在同一步内读到对方尚未提交的写入。
2. 两个节点同时更新一个字段，需要明确合并规则。
3. 检查点通常落在 super-step 边界，不能想象成 Python 每执行一行都自动存档。

节点可包含同步函数或异步函数。异步能提高 I/O 等待阶段的资源利用率，不会自动让 CPU 密集任务更快；也不能在异步节点里放长时间阻塞调用而期待事件循环正常并发。

图的正常停止意味着没有待执行节点 / 活跃消息，或按设计到达结束路径。业务成功是另一回事：到达 `END` 的路径也可能是拒绝、无结果、取消或失败降级。

## 5. 路由：普通边、条件边、Command、Send

| 机制 | 适用情况 | 容易误用的地方 |
| --- | --- | --- |
| 普通边 | 固定前后关系 | 将所有动态逻辑硬塞进节点 |
| 条件边 | 依据状态选择后继 | 路由函数产生不受控副作用 |
| `Command(update=..., goto=...)` | 节点同时更新状态和决定方向 | 以为它会取消同节点已有普通边 |
| `Send` | 按输入集合动态生成并行任务 | 无限制 fan-out 导致调用风暴 |

`Command` 不是“万能跳转”。如果一个节点既有固定出边，又返回动态 `goto`，固定出边不会因此天然失效。应避免意外同时调度多个后继。

动态 fan-out 需要限制任务数量、并发度、每个子任务的输入大小与总预算。Reducer 解决的是结果如何并入 State，不是外部资源的锁或数据库事务。

### 5.1 并行汇合：结果合并与等待完成是两件事

Reducer 决定同一字段怎样合并，join 决定汇总节点什么时候可以运行。固定并行分支需要等待全部完成时，可用列表前驱的边表达共同依赖，例如 `builder.add_edge(["budget", "risk"], "summarize")`。

分别写两条单前驱边，不能在任意复杂、不等长分支中都等价地理解为“只汇总一次且等待全部路径完成”。动态 Send、分支数量变化、分支失败还需明确完成集合和失败策略，并用实际图测试调度结果。

Reducer 应尽量使用纯函数，明确结合性、去重与排序语义。列表拼接有结合性但没有交换性；若业务需要确定顺序，应记录稳定 key 并在汇总时排序，而不是依赖并行完成顺序。

### 5.2 Graph API 与 Functional API

Graph API 用显式 State、节点和边描述流程，适合需要清楚展示路由、共享状态和并行关系的场景。Functional API 用 `@entrypoint`、`@task` 等方式给较普通的 Python 控制流接入相关运行能力。

两者是建模风格选择，不是“有图的才可恢复、函数式就无需理解检查点”。使用 Functional API 时，同样要处理可序列化输入输出、重放、非确定性和副作用；把函数加一个装饰器不会自动让任意外部调用具备事务性。

## 6. 一个不依赖模型的完整小图

下面只使用固定内存数据，演示“产生证据→独立验收→结束”。安装对应依赖后可单独学习；本次文档整理只检查语法，不执行它。

```python
from decimal import Decimal
from typing import TypedDict

from langgraph.graph import END, START, StateGraph


class QueryState(TypedDict, total=False):
    # 状态保存事实和验收结果，不保存模型密钥或外部客户端。
    amounts: list[str]
    total: str
    verified: bool


def calculate(state: QueryState) -> dict:
    # 使用字符串构造 Decimal，避免先经过 float 引入二进制误差。
    total = sum((Decimal(value) for value in state["amounts"]), Decimal("0"))
    return {"total": str(total)}


def verify(state: QueryState) -> dict:
    # 核对节点检查结果，不把“上一步没抛异常”当作成功证据。
    expected = sum((Decimal(value) for value in state["amounts"]), Decimal("0"))
    if Decimal(state["total"]) != expected:
        raise ValueError("金额验收失败")
    return {"verified": True}


builder = StateGraph(QueryState)
builder.add_node("calculate", calculate)
builder.add_node("verify", verify)
builder.add_edge(START, "calculate")
builder.add_edge("calculate", "verify")
builder.add_edge("verify", END)
graph = builder.compile()

result = graph.invoke({"amounts": ["100.10", "1000.10"]})
assert result["total"] == "1100.20" and result["verified"] is True
```

真实项目还需要处理输入金额格式、负数规则、币种、舍入与数据时效；此例只说明编排和验收的分工。

## 7. 持久化、恢复与时间旅行

### 7.1 Checkpointer 记录什么

Checkpoint 不只是消息列表，还包含状态、下一步任务、执行元数据等恢复信息。常见线程配置是 `{"configurable": {"thread_id": "review-001"}}`。

同一 checkpointer 与同一 thread 能定位同一条历史；如果每次请求都随机生成新 thread，通常就不是在恢复旧任务。

`InMemorySaver` 适合教学和进程内测试，进程退出后数据不保留。换成持久化 saver 也不是只换一个类名就万事大吉：连接管理、容量、加密、清理、备份和兼容性都属于部署工作。

### 7.2 Pending writes 的意义

同一 super-step 中一个节点失败时，其他已成功节点的 task-level 写入可以被记录，恢复时不必全部重算。这和“每个成功节点都有一个可任意时间旅行的完整 StateSnapshot”不是一回事。

### 7.3 恢复不是完整进程快照

可以恢复业务状态和调度位置，不会复活旧进程的 TCP 连接、数据库会话、浏览器标签页或临时内存对象。恢复时需要根据状态重新连接外部资源，并确认资源仍有效。

### 7.4 Replay、fork、更新状态

- Replay：从历史检查点继续执行后续节点；后续 LLM 和外部请求可能再次发生。
- Fork：从旧状态探索另一条执行分支，不是把真实世界回滚到过去。
- 更新状态：通常产生新的历史更新，并受 reducer 规则影响，不是随意覆盖底层存档。

检查点能回退图内视图，不能撤销已发短信、已提交订单或已转账。此处必须另谈幂等、补偿与人工处理。

<a id="lg-durability"></a>

### 7.5 Durability 与性能

在配置可用 checkpointer 的前提下，1.2.11 的策略区别应按“何时等待写入、发生哪类故障”解释，而不是按“安全 / 不安全”二选一：

| 策略 | 持久化时机 / 等待关系 | 典型取舍 |
| --- | --- | --- |
| `sync` | 相关检查点写入完成后再进入下一步 | 增加保存等待，缩小进入后续步骤时的未保存窗口 |
| `async` | 保存可与后续执行重叠 | 减少等待；进程在保存完成前硬崩溃，可能丢失尚未持久化的进展 |
| `exit` | 主要在运行退出边界提交，而非逐步持久化 | 减少中间保存开销；进程硬崩溃时不能依靠本次未保存的中间进度恢复 |

`exit` 的“退出”不只指成功完成，也包括运行时正常处理的错误和 interrupt 边界；因此不能说它“不能用于人工审批”。这里的正常处理指退出逻辑确实执行并完成保存，不是所有异常都被业务捕获后继续。断电、进程强杀、存储写入失败不享有相同保证。嵌套子图的具体保存边界还受配置影响。

以上时机对照本地 `pregel/_loop.py` 的退出保存路径；不同 saver 的确认、底层存储耐久性、待执行写入与恢复入口仍需独立验证。即使 `sync`，图内保存与外部业务动作也不是原子提交。

<a id="lg-serialization"></a>

### 7.6 可以读取 checkpoint，为什么仍不能接受任意“恢复文件”？

Checkpoint 是受控执行状态，不应设计成让用户上传任意二进制内容后直接反序列化。恢复接口先验证调用者、thread 归属、来源、格式与版本，再由受控 saver 读取。

- 不因某个对象无法序列化就直接开启 `pickle_fallback=True`；优先把对象转换为可解释的业务数据，把连接和句柄留在 runtime 外部。
- `pickle` 反序列化可能执行代码，不处理不可信数据。关闭 pickle 也不意味着其他对象恢复逻辑天然适合任意输入。
- 本地 `JsonPlusSerializer` 的安全说明明确警告：可直接篡改 checkpoint 存储的攻击者可能利用反序列化触发代码执行。存储写权限、受支持类型限制与依赖安全更新都是边界的一部分。
- 加密主要保护静态内容，不替代对象访问控制，也不证明被恢复任务仍有执行权限。业务权限与审批时效在继续执行前重新确认。

连续追问：“只要 thread_id 足够随机就能公开恢复接口吗？”不能。随机标识降低猜中概率，不能替代认证、归属校验和管理操作审计。这里是安全设计建议，不是本仓库已实现了一套 checkpoint 上传服务。

<a id="lg-interrupt"></a>

## 8. 人工介入：interrupt 不是普通异常提示

`interrupt(payload)` 暂停执行并把可序列化信息交给调用方；恢复时用相同 thread 和 `Command(resume=...)` 提交决定。

关键规则：

1. 配置可用 checkpointer，并保持 thread 关联。
2. 中断 payload 展示待决策对象、参数、风险和必要证据，不暴露密钥。
3. 恢复会重新进入相关节点；`interrupt` 之前的代码可能再次执行。
4. 不用宽泛异常捕获吞掉中断控制信号。
5. 多个中断的调用顺序需要稳定，不能在恢复前后随意重排。
6. 审批必须绑定具体动作和参数版本，不是把“用户说同意”拼进 Prompt。

接口示例只在内存中记录决定，没有业务写入：

```python
from typing import TypedDict

from langgraph.checkpoint.memory import InMemorySaver
from langgraph.graph import END, START, StateGraph
from langgraph.types import Command, interrupt


class ReviewState(TypedDict, total=False):
    request_id: str
    approved: bool


def review(state: ReviewState) -> dict:
    # 恢复时这段节点会重入，因此这里不发送通知、不创建业务记录。
    decision = interrupt({"request_id": state["request_id"], "action": "只记录演示决定"})
    if type(decision) is not bool:
        raise ValueError("决定必须是布尔值")
    return {"approved": decision}


builder = StateGraph(ReviewState)
builder.add_node("review", review)
builder.add_edge(START, "review")
builder.add_edge("review", END)
graph = builder.compile(checkpointer=InMemorySaver())
config = {"configurable": {"thread_id": "demo-review"}}

paused = graph.invoke({"request_id": "demo-001"}, config=config)
assert paused["__interrupt__"]
finished = graph.invoke(Command(resume=False), config=config)
assert finished["approved"] is False
```

真实审批的身份认证、持久化、防重复提交不在此片段中。即使把副作用放到审批后，崩溃重试仍可能重复执行，不能因此宣称 exactly-once。

## 9. 工具循环与多 Agent

经典工具循环：模型节点产生 tool calls → 工具节点校验并执行 → 工具结果回到消息 → 模型继续或结束。

必须保证：工具参数经过校验，tool result 关联正确的调用 ID，危险操作检查权限，工具错误不能伪装成成功数据。

多 Agent 可表现为子图、工具委派、主管路由或 handoff。先问它们是否真的需要独立模型上下文，而不是只因“多 Agent 听起来高级”就拆分。

子图应明确：输入输出 schema、消息是否共享、检查点如何配置、错误向哪里传播、父子预算如何累计。子图不等于权限隔离进程，更不是天然的安全沙箱。

## 10. 流式输出与可观察性

| 信息 | 用途 | 不应误认为什么 |
| --- | --- | --- |
| `updates` | 节点状态增量 | 只包含最终回答 |
| `values` | 某步完整状态视图 | 可以不脱敏直接发给前端 |
| `messages` | 模型消息 / token 相关事件 | 任务已经完成 |
| `custom` | 应用自定义进度 | 框架事实自动保证 |
| 子图 namespace | 区分父子任务事件来源 | 租户鉴权机制 |

仓库流式专题采用 `version="v2"`、`subgraphs=True` 和事件 `type/ns/data` 结构。不要与旧版 tuple 返回形状、`astream_events` 或新文档其他事件 API 混写。

业务日志至少关联 request、thread、run、节点 / 工具、耗时、尝试次数、错误类别。保留可观察的动作理由和证据即可，不要求记录或公开模型完整隐藏推理。

## 11. 工程可靠性：最容易被追问的部分

### 11.1 幂等与外部副作用

“请求超时”可能表示未执行，也可能表示已执行但响应丢失。重试前先对账；写入使用业务幂等键，由服务端去重，必要时使用 outbox、状态机或补偿流程。

幂等键应来自稳定业务动作，例如“申请 ID＋动作类型＋版本”，而不是每次重试生成新 UUID。不要在 reducer 里执行写操作。

### 11.2 错误分类

- 临时网络问题：有限退避重试。
- 格式或可修正输入：回给模型明确纠错信息。
- 权限不足：停止或人工处理，不让模型试其他租户。
- 不确定是否写入成功：进入核对流程，不盲目重放。
- 图逻辑循环：检查路由与终止条件，不仅增加 `recursion_limit`。

### 11.3 预算与并发

`recursion_limit` 控制图执行步数边界，不等价于“模型最多调用几次”。工具并行、子 Agent 和 provider 内重试都可能放大真实调用量。

同时控制图步数、模型请求数、子任务数、超时和总成本。线程级状态隔离也不意味着同一 thread 的并发写入天然安全，需要调用入口串行化或可靠并发策略。

节点缓存也需区分业务身份、输入版本与数据时效，明确 cache key 和 TTL。包含租户权限、实时预算或已变化外部对象的结果，不能因为输入文字相同就跨用户复用；缓存命中不等于本轮重新采集了证据。

### 11.4 测试层次

1. 纯函数：路由、reducer、金额和规则校验。
2. 图集成：固定模型响应，验证分支、循环和状态。
3. 恢复：中断、重建图、同 thread 恢复、重复提交。
4. 副作用边界：mock 客户端，确认未批准时零执行。
5. 真实模型评估：独立数据集、多次运行、统计成功率。

固定响应测试证明接口和控制逻辑，不证明模型能自主规划。示例使用内存模拟，不意味着生产数据库测试可以随意运行。

## 12. 分层问答：基础与执行机制

### Q1：LangGraph 与 LangChain 有什么关系？

**简答：** LangChain 提供模型、工具与 Agent 抽象；LangGraph 更关注有状态执行与编排，LangChain 的现代 Agent 可建立在 LangGraph 上。

**深入：** 一个是更高层的应用组件和循环，一个是执行控制基础。选型不是二选一，可以用 LangChain 组件构建自定义 LangGraph。

**追问：** 不使用 LangChain 模型也能用 LangGraph 吗？可以，节点本质上是受图运行时调用的函数 / Runnable。

**误区：** “必须先学完所有 LangChain 组件才能用 LangGraph”。

### Q2：为什么不用 while 循环自己写 Agent？

**简答：** 简单任务可以。复杂任务的成本在状态持久化、暂停恢复、并发、事件和故障处理，而不只是循环本身。

**深入：** 自写循环要补齐恢复协议、消息关联、幂等和可观察性。LangGraph 提供统一执行模型，但仍需业务规则。

**追问：** 什么情况下你仍选 while？范围小、步骤短、无跨进程恢复需求且测试可覆盖时。

**误区：** 为两步固定脚本引入完整复杂图。

### Q3：节点返回完整 State 与返回部分更新有何区别？

**简答：** 推荐返回需要变更的字段，避免无意覆盖其他节点的数据。

**深入：** 返回值不是直接替换全局字典，而是按字段 reducer 应用。返回整个旧列表给追加 reducer，可能把旧元素再次追加。

**追问：** 怎样定位消息重复？检查节点是否返回旧历史＋新增消息，同时 reducer 又进行追加。

**误区：** 以为返回越完整越安全。

### Q4：Reducer 能解决什么，不能解决什么？

**简答：** 它定义图状态字段的合并，不负责外部事务、权限或业务去重的全部语义。

**深入：** 并行结果可以用 reducer 汇聚，但顺序、重复项和冲突要明确。合并逻辑应可预测，重放语义要稳定。

**追问：** `operator.add` 能避免重复订单吗？不能，需要稳定 ID 和显式去重策略。

**误区：** 给所有字段加列表拼接就解决并发。

### Q5：条件边与 Command 应怎样选？

**简答：** 单纯按状态路由用条件边；需要在节点返回值中同时表达更新和跳转时用 Command。

**深入：** 关键是保持单一清晰的控制来源，避免固定边与动态跳转共同激活意外路径。

**追问：** Command 会取消普通边吗？不会天然取消。

**误区：** 把 Command 当异常式 goto。

### Q6：`Send` 与普通并行边有什么区别？

**简答：** 普通并行边的后继一般在建图时确定，Send 可根据运行时集合生成多个任务及各自输入。

**深入：** 适合 map-reduce 型任务，但 fan-out 规模和汇聚结果必须受控。

**追问：** 处理一万条数据能直接创建一万个模型子任务吗？应批处理、限流并预算约束，而非无界派发。

**误区：** 并行越多吞吐必然越高。

## 13. 分层问答：恢复、审批与生产问题

### Q7：有 Checkpointer 就能保证任务只执行一次吗？

**简答：** 不能。检查点保证的是图恢复能力，不是外部系统 exactly-once。

**深入：** 外部写入成功、检查点写入前崩溃是典型重复风险窗口，需要业务幂等键与对账。

**追问：** 把写入拆成独立节点就够了吗？只是缩小风险边界，不能替代服务端去重。

**误区：** “可恢复＝不会重复执行”。

### Q8：为什么恢复 interrupt 时，前面的代码又运行了？

**简答：** 恢复会重新进入中断所在节点，不是保存 Python 调用栈后原地继续。

**深入：** 中断前不要放非幂等副作用；调用顺序和条件分支必须稳定。

**追问：** 怎样避免重复通知？独立动作节点＋稳定幂等标识＋外部去重。

**误区：** 以为 `interrupt()` 与 `await` 的资源保存语义完全一样。

### Q9：Store 与 Checkpointer 能否相互替代？

**简答：** 不能直接替代。Checkpointer 管 thread 执行历史，Store 管跨 thread 的资料。

**深入：** 用户偏好可以放 Store，本任务暂停点由 checkpoint 记录；二者都要配置租户边界。

**追问：** 把所有历史塞进一个全局 Store 可以吗？会引入隐私串线、检索噪声和一致性问题。

**误区：** “长期记忆就是把 messages 永久存下来”。

### Q10：图能重建后恢复，为什么浏览器不能直接恢复？

**简答：** 图保存的是序列化执行状态，不是外部进程和浏览器会话的完整快照。

**深入：** 需要重新建立浏览器控制连接、核对认证和当前页面，再决定恢复动作。

**追问：** 状态里保存 URL 就够吗？不够，页面数据、sessionStorage、弹窗和权限可能已变。

**误区：** 把浏览器 Page 对象写入 State。

### Q11：流式输出中出现最终文本，是否就能显示任务成功？

**简答：** 不能。文本增量、模型结束、图结束和业务验收是不同事件。

**深入：** 前端区分运行中、待审批、部分结果、已验收、失败；完成标记应由可信后端产生。

**追问：** 已发送的部分结果后来校验失败怎么办？明确标记未验收，不能让临时输出触发业务写入。

**误区：** 收到最后一个 token 就更新订单为成功。

### Q12：为什么出现 `GraphRecursionError`？

**简答：** 通常表示图在步数上限内没有结束，可能是正常长任务，也可能是路由或工具循环有问题。

**深入：** 检查重复状态、同一失败工具、终止条件和预算，不应第一反应无限调高上限。

**追问：** 怎么发现“有动作但没进展”？比较阶段、证据数量、目标重复和错误类型。

**误区：** 把它直接归因于 Python 函数递归过深。

### Q13：节点失败后该怎样重试？

**简答：** 先区分临时失败、权限失败、业务失败和结果不确定，再选不同恢复策略。

**深入：** 可以重试读取，但未知写入结果先核对；全图重跑可能重复已完成副作用。

**追问：** 429 与参数不合法都指数退避吗？前者可能适合，后者通常应修正输入。

**误区：** 捕获所有异常后返回空列表并继续成功。

### Q14：同一 thread 能同时处理两个请求吗？

**简答：** 需要明确并发策略，不能仅因框架支持并行节点就认为并发请求安全。

**深入：** 同一任务的两次恢复、两个人同时审批可能竞争。入口需要锁、排队、版本检查或服务层规定的运行策略。

**追问：** 用不同 thread 避免竞争行吗？那变成两条执行历史，外部同一业务对象仍可能冲突。

**误区：** thread ID 自动承担业务锁。

### Q15：如何回答“你用 LangGraph 做过什么”？

**简答：** 用任务目标、状态设计、控制流、恢复策略和验收结果来讲，不只报框架名。

**深入：** 例如采购评审：可信身份上下文→确定性金额计算→专家证据→规则验收→必要时人工审批→受控执行。

**追问：** 最难的问题是什么？可谈中断重入、副作用幂等、并行更新冲突，以及你怎样设计测试。

**误区：** 将学习示例说成已生产落地、具备未经测量的成功率。

## 14. 三道场景题的作答框架

### 场景 A：审核员第二天回来继续审批

答案顺序：持久化 saver → 稳定 thread → 审批人认证 → 展示当前动作与版本 → 提交绑定中断的决定 → 重新验证业务前置条件 → 幂等执行 → 审计。

要补一句：隔夜业务数据可能变化，旧审批不能无条件套在新金额上。

### 场景 B：三个专家并行评审，一个失败

先定义结果字段与 reducer；专家任务有独立 ID 和超时。可以保留成功结果，对失败分支有限重试；缺失关键专家结果时只能返回不完整，不能由主管凭空补齐。讨论 pending writes 时区分任务写入与完整检查点。

### 场景 C：恢复后重复创建了订单

先停止自动重试并核对外部结果，再检查幂等键是否稳定、业务服务是否去重、写入与 checkpoint 之间的崩溃窗口。修复方案要落在外部操作协议，不能只改 Prompt。

## 18. 高级追问：从知道名词到解释执行结果

以下 H 题是在前面 Q 题之上的第二轮、第三轮面试。回答顺序建议是“先给结论→说明执行边界→举失败反例→说明怎样验证”。应用层方案不代表 LangGraph 默认提供。

速查：并发与合并看 H1–H3；保存与副作用看 H4–H5；审批与竞争看 H6–H7；子图、重放、升级看 H8–H10；流式与缓存看 H11。练综合题时先遮住第 19 节答案，限时十分钟陈述。

### H1：两个并行节点读写同一字段，为什么不能按普通共享变量理解？

**第一问：** A、B 同一步被激活，初始 `count=0`；A 返回 1，B 返回 2，最后是多少？

不能脱离 channel / reducer 作答。普通单值字段不接受这种并发写入，可能报并发更新错误；加法 reducer 才可能把两份增量合并。节点返回的是“增量”还是“新总值”也必须说清楚，否则即使程序不报错，结果仍可能错误。

**追问一：B 晚启动一秒，能读到 A 的 1 吗？** 不应依赖这个时间差。同一 super-step 的更新在步边界提交，兄弟节点按该步输入工作；需要看 A 的结果，必须表达执行依赖，让 B 在后续步读取。

**追问二：A 直接修改传入 State 的嵌套列表呢？** 不要利用对象引用共享作为通信协议。这会绕过清晰的更新通道，影响重放、并发和测试。节点应构造更新，合并由 reducer 完成；外部可变资源也不能偷偷充当状态 channel。

**追问三：怎样验证？** 用固定输入、可控延迟和无模型节点，改变 A/B 耗时，检查结果仍符合定义；检查依赖而不是测试“谁先跑完”。睡眠只能用于故障模拟，不能修复依赖关系。

<a id="lg-reducer"></a>

### H2：Reducer 的结合性、交换性、幂等性分别解决什么？

**第一问：** `operator.add` 有什么问题？列表拼接有结合性，但不交换、不幂等。它适合保留多份结果，不适合自动承担排序或业务去重。

**追问一：三个性质有什么差别？** 结合性保证分组方式变化不改变结果；交换性保证输入排列不影响结果；幂等性保证同一更新重复应用不增加影响。不要说“LangGraph 强制任何 reducer 都满足三者”：是否需要取决于 channel、调度和业务协议，尤其顺序敏感数据可能本来就不交换。

**追问二：既然有检查点，为什么还考虑幂等？** 正常恢复不会无条件把所有已提交更新再加一次；但应用重发输入、重复事件、错误返回整份旧 State，仍可能造成重复。不能用“框架一定重复”解释所有重复，也不能用检查点消除业务重投风险。

**追问三：按 ID 去重就够了吗？** 同 ID 不同内容可能是真实冲突。先定义 ID 指业务对象还是证据事件，再定义版本与冲突策略；`dict.update` 的后到覆盖不是通用解。

纯本地反例与最小合并器，只演示数据规则，不调用图或外部服务；本次仅检查语法：

```python
from operator import add

# 拼接不会自动去重：重复交付同一事件会改变列表。
assert add(["event-a"], ["event-a"]) == ["event-a", "event-a"]

# 每条证据由稳定 ID、单调版本、不可变正文构成；合法输入要求同 ID 同版本正文唯一。
Evidence = dict[str, tuple[int, str]]


def merge_evidence(left: Evidence, right: Evidence) -> Evidence:
    # 不修改输入，避免兄弟节点、历史快照或调用方被连带修改。
    merged = dict(left)
    for evidence_id, incoming in right.items():
        current = merged.get(evidence_id)
        if current is not None and current[0] == incoming[0] and current != incoming:
            # 这里只能发现参与本次比较的同版本冲突，不是完整历史冲突检测器。
            raise ValueError(f"证据版本冲突：{evidence_id}")
        if current is None or incoming[0] > current[0]:
            merged[evidence_id] = incoming
    return merged


a = {"budget": (1, "虚构预算证据")}
b = {"inventory": (1, "虚构库存证据")}
assert merge_evidence(a, a) == a  # 相同证据重复交付不增加影响。
assert merge_evidence(a, b) == merge_evidence(b, a)  # 无冲突更新不依赖排列。
```

**保证边界：** 这里保留的是每个 ID 的最新版本，不是完整审计日志。只有所有输入都遵守“同 ID、同版本唯一正文”的协议时，才能把它当作按版本取最大值的合并；上述两条断言不能证明任意输入上都结合、交换且可靠报告冲突。

反例：同一个 ID 的三份更新分别为 `v1:A`、`v1:B`、`v2:C`。先合并两份 v1 会抛冲突；先把 `v1:B` 与 `v2:C` 合并，再合并 `v1:A`，旧版冲突就被最高版本掩盖。这不是 LangGraph 调度错误，而是“只存最高版本”的信息损失；异常结果会随分组变化。

若不能在可信入口建立该唯一性约束，应先保留不可变证据事件及其来源，在受控验收阶段检查同版本分歧，再投影出当前值；不要声称一个 latest-value reducer 就提供了全历史冲突检测或完整 CRDT 保证。测试至少覆盖输入排列、分组、重复、相同版本不同正文，以及升级后收到迟到旧版本。

### H3：不等长并行分支，为什么可能提前汇总或多次汇总？

**第一问：** `START→A→C` 和 `START→B→B2→C`，C 会不会自动等全部？不能凭图形直觉判断。单前驱边表达各自触发关系，不等于一条声明完整依赖集合的 join；应明确 C 等的是 A 与 B2，而不是 A 与 B。

**追问一：加 reducer 就能等齐吗？** 不行。Reducer 处理已经到达的更新；join 处理什么时候调度。一个能正确合并部分结果的 C，也可能在证据不全时得出错误完整结论。

**追问二：动态 Send 没有固定前驱列表怎么办？** 对标准同一轮 map-reduce，可利用其 super-step 汇聚；如果每项还有不同深度子流程、重试或远程任务，就要在应用状态记录预期任务 ID 集合及每项终态，明确“全部完成”“可部分完成”“超时关闭”的判据，不能套用所有分支天然同深度的假设。

**追问三：一个分支被拒绝访问算完成吗？** 执行上可到达终态，业务上可能不满足验收。汇总必须区分 succeeded、denied、failed、cancelled，不能只比较结果条数。

**验证点：** 覆盖零项、一项、重复项、不等长、部分失败、超时和恢复；断言汇总触发次数，以及它看到的任务集合与最终状态。

### H4：Pending writes 到底能省掉哪部分重跑？

设某个 super-step 同时执行 A、B，故障时序如下：

| 时点 | 已发生的事 | 恢复时需要知道什么 |
| --- | --- | --- |
| T0 | 上一步完整 checkpoint 已保存 | 当前步的输入可重建 |
| T1 | A 成功，其 task writes 已可靠保存 | 可以复用 A 的已保存结果 |
| T2 | B 执行失败 | B 仍需按恢复策略处理 |
| T3 | 调用方以正确配置恢复 | 不是从零重新执行整张图 |

**追问一：A 成功就一定不再跑吗？** 还取决于其结果是否真的成功保存、采用的 saver / durability、故障位置和恢复方式。T1 如果只是函数返回、写入尚未可靠保存，就不能套用同一结论。

**追问二：这等于 A 有一个完整 checkpoint 吗？** 不是。Task-level writes 可用于当前失败步的恢复，不等于每个节点结束都形成独立、完整、可随意分叉的快照。

**追问三：A 中的外部写入也被保证了吗？** 没有。A 的外部服务响应和 task writes 不处于同一原子事务。外部写入成功而本地记录失败，仍可能重复执行。

**验证点：** 故障注入必须区分“节点失败”和“保存失败”，观察实际调用计数与外部动作 ID；不能只在 B 里抛一次异常就宣称覆盖所有宕机窗口。

### H5：把外部写入拆成独立节点，为什么还不是 exactly-once？

**第一问：** “审批节点→创建订单节点→保存结果”，哪里会重复？外部创建成功后、结果 checkpoint 保存前崩溃，恢复可能再次进入创建节点。

**追问一：先 checkpoint 再创建呢？** 会换成另一种窗口：状态说已执行，但创建还没发生。两个系统之间仅调换顺序不能得到原子性。

**追问二：完整方案是什么？** 为同一业务意图固定 action_id 与参数摘要；业务端原子去重，相同 key / 相同参数返回旧结果，相同 key / 不同参数拒绝。超时进入 unknown_outcome，通过 action_id 查执行结果，再决定续跑或人工处理。

**追问三：旧 checkpoint 分叉再跑，要用旧 key 吗？** 先定义意图。如果只是恢复同一动作，应沿用；如果是授权后的新业务动作，要生成新的业务版本与 key。不能按每个 graph run 随机生成 key，也不能把所有未来动作永久合并为同一个 key。

**追问四：业务端不支持去重或按动作查询？** 自动恢复能力必须降级。记录不确定状态、停止盲重试、人工核对。框架不能替不支持的外部系统凭空创造 exactly-once。

### H6：一个节点里两个 interrupt，恢复为什么会串审批？

**第一问：** 先审批金额，再审批收件人；恢复时临时增加一个条件中断会怎样？节点重入依赖稳定的中断调用顺序，前后分支或顺序变化可能使恢复值不再对应原问题。

**追问一：怎么设计稳健？** 把审批阶段拆清楚，状态记录 proposal_id、参数版本和决定；涉及多项并发中断时按当前版本提供的中断标识协议恢复。不要仅靠“第一个布尔值、第二个布尔值”的 UI 猜测对应关系。

**追问二：为什么不能宽泛捕获？** `interrupt` 使用特殊控制信号暂停图。广泛捕获可能吞掉中断，让节点错误继续。将容易失败的业务代码与中断调用分开，按具体异常类型处理；不能通过“捕获到异常就批准”消除报错。

**追问三：审批后就不会变了吗？** 不会。审批期间对象可能被别的用户修改。执行前校验对象版本、当前权限、金额与有效期，变化后重新生成提案，不把旧批准应用于新参数。

**验证点：** 连续两次中断、拒绝后再次申请、审批过期、重复恢复、参数变化、节点代码升级，分别检查决定究竟绑定哪份提案。

### H7：同一个 thread 同时收到两条恢复请求，谁说了算？

**第一问：** 两个人先后点击同意，thread_id 相同就能防重吗？不能把历史定位键当业务互斥锁；裸图调用、服务部署与托管运行策略也不能混为一谈。

**追问一：怎样避免竞争？** 在应用入口对同一任务使用串行队列、单飞策略或可靠版本检查。多 worker 场景可用持久租约与 fencing token 阻止旧 worker 继续提交；这是通用分布式设计，不是 StateGraph 默认分配的能力。

**追问二：锁住 thread 就能防重复业务动作吗？** 两个 thread 仍可操作同一申请。业务 action_id、对象版本与服务端幂等还要独立成立。

**追问三：thread_id 用 UUID 就安全吗？** 不可猜测只能降低枚举风险，不能替代鉴权。读取历史、恢复、更新状态、下载产物都必须校验 thread 所属租户与当前用户权限。

**验证点：** 两个 worker、两个审批请求、过期锁持有者、其他租户读取同一 ID；测试不仅看返回码，还看实际外部调用次数。

### H8：父子图共享消息时，为什么常出现重复或状态污染？

**第一问：** 父图 messages 用 add_messages，子图返回完整历史就一定重复吗？不能一概而论：相同消息 ID 可被更新，新 ID 的相同文本仍可能成为重复。要检查返回契约、消息 ID 和 reducer，而不是只比较文本。

**追问一：子图与父图 schema 不同怎么办？** 用适配节点明确映射输入输出；不要默认所有字段都会自动安全传播。需要共享的字段、私有字段与跨图返回的 Command 都应有明确约定。

**追问二：父有 checkpointer，子会自动怎样保存？** 看子图的编译配置和调用方式。继承父检查点的常见模式，与子图显式独立持久化的模式不是同一个生命周期；namespace 区分执行位置，不是跨租户授权。

**追问三：同一子图并行调用能共享可变对象吗？** 不应。输入是逻辑隔离也不等于客户端、Store 或宿主文件隔离。应用仍需定义资源边界，必要时每个任务独立命名空间。

### H9：Functional API 看起来像普通 Python，为什么仍要考虑重放？

**第一问：** `@entrypoint` 里取当前时间、随机数、调用接口，再执行 `@task`，恢复会怎样？恢复可能重新运行入口控制逻辑，并从保存结果中复用已完成 task；未封装的非确定性逻辑可能变化，造成与原结果不一致的路径。

**追问一：怎样划分 task？** 把需要稳定复用的非确定性结果和外部动作放到适当 task 边界，保存可序列化结果。不要为每行代码拆 task，也不要把整个超长流程塞成一个 task。

**追问二：封成 task 就能安全扣款吗？** 仍不能。Task 返回值保存前崩溃的窗口依旧存在，外部动作必须有幂等协议。

**追问三：恢复前改了调用顺序呢？** 可能破坏历史与新逻辑的对应。长跑任务应固定代码版本，升级需要明确兼容策略；不能以“都是 Python 函数”忽略执行历史。

### H10：状态 schema 升级时，暂停一周的任务怎样继续？

**第一问：** 把 `amount` 改名 `total` 后直接恢复旧 checkpoint 可以吗？旧记录、reducer 输入、节点名、待执行任务都可能与新版不兼容。增加带默认值的字段通常比删除 / 改名更容易兼容，但也需实际验证。

**追问一：可选方案？** 固定旧运行到旧代码；对可兼容更改做显式适配；确需迁移时，定义状态版本、迁移函数与回滚策略，并在历史样本副本上验证。不是建议直接改底层 checkpoint 数据。

**追问二：外部工具 schema 也变了怎么办？** 固定或适配工具契约；旧审批绑定旧参数版本。不能在恢复时把已批准的旧工具调用悄悄映射为影响更大的新操作。

**追问三：怎样判定升级成功？** 不只看能反序列化，还需检查从旧暂停点继续后的路由、审批、动作 ID、结果与权限均正确。

### H11：流式断线、缓存命中、取消，为什么容易让前端误报成功？

**第一问：** 浏览器收到最后一段回答后断线，后端任务算完成吗？最后文本、图终态和业务验收可能不同步；前端应按可信任务状态查询，事件只作增量展示。

**追问一：怎样断点续看？** 应用事件层可用 run_id＋单调 event_seq，前端按序去重、补拉；检查点不是直接给 SSE 当日志用。慢消费者要有缓冲限额与降采样，不能无限积累 token 事件。

**追问二：取消后为什么还有工具结果？** 已发出的远程请求未必能撤回，取消可能只停止后续调度。明确 cancelling 与 cancelled、已完成动作及未知结果，不在 UI 上提前宣称回滚。

**追问三：缓存命中能当本轮核对证据吗？** 只有在契约接受其版本和时效时。缓存键至少考虑租户、身份范围、数据 / 工具版本与输入；授权不能只因历史缓存命中继续生效。缓存纯解析与缓存实时业务事实，风险不是一个级别。

## 19. 综合系统设计：隔夜审批＋并行证据＋可恢复执行

**题目：** 采购申请需要预算、库存和供应商证据，允许次日人工审批；服务可能重启，外部写入偶发超时。请说明如何用 LangGraph 组织，不要求现场写生产服务。

### 19.1 一个可站得住的参考方案

1. 入口先认证并限定 tenant，创建业务 request_id 与独立 thread 映射。State 只存可序列化提案、版本、证据引用和动作状态，不存连接或秘密。
2. 确定性节点计算金额，随后有限并行收集三类证据。结果含 evidence_id、来源版本、观测时间、状态；汇合按明确完成集合判断，不能让失败变成“预算为零”。
3. 模型生成建议，代码校验引用、金额、证据完整性。缺失关键证据进入待补充 / 失败终态，不进入“批准执行”。
4. 固化提案参数摘要及业务对象版本后 interrupt。审批界面展示实际提案，服务端验证审批人、有效期、同一提案与单次决定。
5. 恢复后重新检查权限、对象版本、必要实时条件。变化时使旧提案失效；未变化才进入幂等动作节点。
6. 外部写入用稳定 action_id；响应丢失则记 unknown_outcome 并对账。确认结果后保存业务验收和最终产物，允许模型生成解释但不再更改事实。

### 19.2 面试官继续质疑时怎样回答

**“三个证据接口不是同一时刻读取，会不会不一致？”** 会。Checkpoint 只能记录图内视图，不能制造外部跨服务快照。定义允许的新鲜度与一致性等级；如果是实际占用预算，最终动作必须由业务系统原子检查前置条件。只做建议则标明证据时点，不能宣称事务级一致。

**“审批期间供应商被停用了呢？”** 执行前重验关键资格。版本匹配仍不足以涵盖所有外部规则时，业务端应再次判定；审批不是绕过业务服务校验的许可证。

**“保存 checkpoint 的服务挂了，但创建请求已经成功呢？”** 走 action_id 对账，不使用随机新 key 重发。任务保持可识别的不确定状态；如果无法对账，应人工处理，而不是把异常吞掉返回成功。

**“能不能每个节点都自动重试三次？”** 不行。只读瞬态失败可重试；权限拒绝不重试；外部写入按幂等能力与结果确定性决定；整个任务还受统一预算与期限约束。

**“为了简单不用 LangGraph 行吗？”** 可以，用队列、状态机和持久化自行实现也可满足目标。选择 LangGraph 是为复用编排与恢复机制，不是宣称没有它就不能做；复杂度仍主要来自业务协议。

## 20. 自测、源码阅读入口与评分标准

**源码阅读路径，按职责理解而非死背私有函数名：** 本地 `langgraph/graph/state.py` 看状态与编译，`channels/` 看 channel 更新，`pregel/` 看调度与执行，`types.py` 看 Command / Send / interrupt / durability 类型，独立 checkpointer 包看序列化与保存契约。私有实现会变，追踪时对照 1.2.11。

建议在不接模型和真实数据库的测试环境中设计以下回归，本次没有执行这些实验：

| 故障或输入 | 最关键的断言 |
| --- | --- |
| 两节点并发写单值字段 | 明确拒绝冲突，而不是依赖耗时先后 |
| reducer 重复 / 乱序输入 | 符合定义的去重、排序与冲突策略 |
| 并行一步部分失败 | 已可靠保存结果按契约复用，缺失结果不伪造 |
| 审批重入与重复提交 | 不产生重复通知或重复业务动作 |
| 外部成功、保存前故障 | 以原 action_id 对账，不另造动作 |
| 同 thread 双恢复 | 只有合法竞争者推进，其他请求得到明确状态 |
| 旧 checkpoint 加新代码 | 有可解释的兼容 / 拒绝，不静默换语义 |
| 流断开后任务继续 | 重连能查真实终态，临时文本不触发成功 |

**答题评分：** 只会列 State / Node / Edge 属于入门；能解释 reducer、super-step、中断重入属于会用；能推演保存窗口、并发竞争、跨版本与外部事实边界，且提出可验证方案，才进入中高级工程回答。不要用未经测试的“框架保证”填补未知。

## 21. 白板演练：给定代码，推算状态与执行顺序

这部分不再复述恢复与幂等原则，而是训练能否从代码推出结果。题目均为固定内存数据，本次只检查代码语法，不运行图。

### W1：兄弟节点读到什么，汇总节点读到什么？

给自己三分钟，回答：left / right 的返回内容分别是什么？report 一共几项？列表顺序是否就是完成顺序？

```python
import operator
from typing import Annotated, TypedDict

from langgraph.graph import END, START, StateGraph


class State(TypedDict):
    # 分支只返回新增项目；历史列表由 reducer 合并。
    items: Annotated[list[str], operator.add]
    report: list[str]


def left(state: State) -> dict:
    # 同一步兄弟节点不应依赖对方尚未提交的更新。
    return {"items": [f"L saw {len(state['items'])}"]}


def right(state: State) -> dict:
    return {"items": [f"R saw {len(state['items'])}"]}


def collect(state: State) -> dict:
    # 业务输出显式排序，避免把调度顺序当业务顺序。
    return {"report": sorted(state["items"])}


builder = StateGraph(State)
builder.add_node("left", left)
builder.add_node("right", right)
builder.add_node("collect", collect)
builder.add_edge(START, "left")
builder.add_edge(START, "right")
builder.add_edge(["left", "right"], "collect")
builder.add_edge("collect", END)
graph = builder.compile()

result = graph.invoke({"items": ["seed"], "report": []})
# 固定断言只依赖已定义的合并和排序，不依赖两个分支的耗时。
assert result["report"] == ["L saw 1", "R saw 1", "seed"]
```

<details>
<summary>参考推演与判分点</summary>

先忽略内部输入处理 / 记账步骤，仅看业务节点：

| 业务步 | 节点读取的 items | 返回的更新 | 步结束后的含义 |
| --- | --- | --- | --- |
| 分支步 | 两个分支均看到 `[seed]` | 各返回一条带 saw 1 的记录 | items 包含原值与两条增量 |
| 汇总步 | 合并后的三条记录 | 返回排序后的 report | report 有三项，图走向结束 |

不能说 right 一定看到 left 的结果，也不能说谁先完成谁就一定排在前面。即使某版本对合并排列有稳定实现，也不要把它解释为业务所需的时间顺序。

追问变体：若 left 返回 `state["items"] + ["L"]`，会把 seed 再提交给拼接 reducer，所以原值重复；若去掉 items 的 reducer，两个分支同一步写单值 channel 会冲突；若 collect 也返回旧 items，则又把历史当增量提交。

评分：同一步可见性 1 分；指出节点应返回增量 1 分；说清 join 与 reducer 不同 1 分；不依赖完成顺序 1 分；能解释三个变体 1 分。

</details>

### W2：人工编辑状态，为什么改一个数字也可能调度后续节点？

已保存状态是 `items=[A]、verdict=pending`。items 使用列表追加 reducer；review 节点的后继是 execute。管理员准备调用 update_state，把 items 改成 `[B]`，同时将 verdict 改为 approved，并指定 as_node=review。

请回答：items 会不会直接变为 `[B]`？review 函数是否被调用？后续可能发生什么？人工编辑能否代替真正审批？

<details>
<summary>参考答案：数据更新、来源标记、授权必须分开</summary>

1. update_state 走状态字段的 reducer 规则，追加型字段通常变为 `[A, B]`，不是无条件替换。不同 channel 的行为不同，不能用一个“更新”词抹平。
2. as_node 表达“把这些更新视为来自该节点”，不等于调用 review 的 Python 函数。它可能影响后续调度；不能理解成仅用于日志显示的标签。
3. 更新一般形成新的 checkpoint 配置，继续时应明确使用返回的配置 / 历史位置，不盲目丢弃返回值，尤其在从旧 checkpoint 分叉时。
4. 把 verdict 设为 approved 并不产生合法审批凭据。执行节点必须独立检查可信审批对象与业务条件，否则有权编辑状态的人可能绕过原本的审批逻辑。

这里的关键不是记住某个私有实现，而是认识：状态编辑 API 同时涉及数据语义和执行语义，是应受鉴权与审计的管理能力。需要替换已有消息时，还要理解 add_messages 的 ID 更新 / 删除协议，不能把列表拼接方案直接照搬过去。

扣分回答：“update_state 就是直接改字典；as_node 写哪个都一样；图状态写 approved 就说明已经批准。”

</details>

### W3：三种“继续”入口，为什么不能互换？

分别给出三个现场：

- 现场 A：节点在 interrupt 处等待审核员选择。
- 现场 B：一个普通节点因临时异常失败，计划从已保存历史继续执行。
- 现场 C：上一轮已结束，用户在同一会话提出一个新问题。

<details>
<summary>参考答案与常见误判</summary>

| 现场 | 常见调用意图 | 需要特别确认 |
| --- | --- | --- |
| A | 以 Command(resume=决定) 交回中断结果 | 同 thread、正确中断、合法审批决定 |
| B | 在相应配置上无新输入继续，例如 invoke(None, config) | saver 中的待执行任务、错误分类、版本与副作用状态 |
| C | 提交新的输入更新 / 消息 | 历史如何合并、旧状态是否仍适用、身份与预算是否正确 |

表中是常见 Graph API 意图，不是所有服务端部署入口都使用相同 HTTP 载荷。恢复失败步不是重新提交一份初始 State；新的问题也不是把 None 当用户消息。混用会造成重复输入、旧任务未处理或错误续跑。

追问：“为了避免重复，把 thread_id 换掉呢？”这会开始另一条历史，不能代替恢复；同一外部业务动作仍可能重复。应该先识别想恢复什么，再选择入口。

评分重点：能区分中断恢复、故障恢复、新轮输入；能说明调用前读取可信任务状态的必要性，而不靠用户说一句“继续”猜测。

</details>

## 22. 容易漏答的契约：State 的输入、内部与输出不必相同

### 22.1 为什么不把内部全部状态直接当输出？

模型消息、工具错误、审批详情、内部证据与用户可见报告用途不同。Graph API 可按版本支持的 input_schema / output_schema 等明确输入输出视图，但投影只是接口边界，不是完整保密方案：checkpoint、日志、values 流和运维查询仍可能看到内部数据。

面试追问：“输出里没有 token 就安全了吗？”如果 token 曾进入 State，仍可能被持久化与追踪；优先从源头不存秘密，可信客户端由 runtime 提供。输出投影不能倒过来清除已保存内容。

### 22.2 路由返回值和类型注解，谁真正决定下一步？

条件函数运行时返回的目标、映射配置和图定义共同决定调度；Literal 等注解可帮助静态理解、检查或图展示，不替代运行时业务分支的正确性。给模型原始字符串直接当节点名，等于让生成结果进入控制面，应先映射成有限、校验后的动作。

错误分支不能默默落到执行节点。未知类型应明确拒绝或走安全错误路径；“有默认 else”不代表默认方向合理。

### 22.3 Reducer 失败后，把冲突吞掉为什么危险？

证据冲突可能揭示版本不一致，直接返回旧值会使任务表面成功且不知丢了数据。可以把预期业务冲突提前转换成显式状态，由汇总节点处理；真正协议错误则应失败并留证。Reducer 里不做模型调用、外部查询或依赖时间的决策，避免合并变成不可重放的副作用过程。

相关机制见本篇 [H2](#lg-reducer)；为什么事实冲突不能按多数票解决，见 [Agent 工程中的证据支持](./05_agent_engineering.md#eng-evidence)。
