## 1. 一句话定位：为什么叫 Harness

Deep Agents 是组装复杂任务执行能力的 Agent harness。除了模型与普通业务工具，它还组织文件工作区、上下文压缩、技能加载、任务委派、人工控制等能力，让长任务有一个可工作的执行环境。

“Harness”可以理解为模型外面的执行支架：模型提出动作，支架决定有哪些工具、怎样接收结果、如何控制上下文、什么时候暂停、怎样保留状态。

它不是训练方法，不会给模型增加新的模型权重，也不意味着模型自动拥有更深推理。任务质量仍取决于模型、工具、任务定义、证据、权限和验收。

## 2. 与其他技术的关系

| 对象 | 负责什么 | 典型提问 |
| --- | --- | --- |
| 模型 | 根据上下文选择下一动作或生成输出 | “下一步应该查什么？” |
| LangChain Agent | 模型 / 工具循环、消息与 Middleware | “怎样执行工具并把结果送回？” |
| LangGraph | 状态、调度、检查点、中断和恢复 | “任务怎么继续、怎么恢复？” |
| Deep Agents | 文件、技能、子任务和上下文管理的组合 | “长任务需要怎样的工作环境？” |
| 业务应用 | 鉴权、预算、审批、外部执行和事实验收 | “这个用户究竟有权做什么？” |

复杂任务不一定需要 Deep Agents。短任务只要类型化工具与输出，可选 PydanticAI；严格阶段流程可能优先用 LangGraph；页面操作还需要浏览器执行层。

## 3. `create_deep_agent` 的构建与运行

构建阶段：选择模型、组装 Middleware、注册工具和子 Agent、确定文件 Backend、编译图。构建不等于已经运行任务。

运行阶段：输入 messages 与上下文 → 模型决策 → 调用工具 / 委派任务 → 工具结果进入状态 → 继续模型循环 → 返回结果或中断。

`create_deep_agent(...)` 返回可执行图，不是一个自动永远驻留的后台工作线程。同步委派会等子任务返回；远程后台任务有独立机制。

重要参数按职责分组：

| 参数 | 用途 | 不应误解 |
| --- | --- | --- |
| `model` | 显式模型对象 / 配置 | 安装框架不等于拥有模型服务 |
| `tools` | 自定义业务能力 | 不代表只剩这些工具，默认栈可能还注册文件 / 委派工具 |
| `system_prompt` | 角色与行为指引 | 不是强制权限系统 |
| `middleware` | 修改生命周期、工具执行等 | 顺序、同名覆盖会改变行为 |
| `backend` | 文件存储及执行能力的后端 | 不是 LLM provider |
| `skills` / `memory` | 技能目录 / 记忆文件来源 | 不是两种相同的长提示词 |
| `subagents` | 声明、编译或远程子任务配置 | 不自动带来独立安全隔离 |
| `checkpointer` / `store` | thread 恢复 / 跨 thread 数据 | 内存实现不等于持久化服务 |
| `context_schema` | 本次可信上下文的结构 | 不让模型自行填写租户和角色 |
| `interrupt_on` / `permissions` | 工具审批 / 文件权限规则 | 不能替代所有业务工具的鉴权 |

## 4. 规划：Todo 不等于可靠工作流

### 4.1 规划解决什么

长任务容易遗漏步骤、重复工作或失去目标。Todo 把目标拆成可追踪事项，如采集预算、核对库存、检查供应商、形成建议。

计划应包含依赖与完成条件，而非只有“分析→执行→总结”三个空词。计划可以依据新证据更新，但不能绕过原授权边界。

### 4.2 当前版本的重要差异

仓库 0.7.x 的规划专题显式添加 `TodoListMiddleware()`，提供 `write_todos`。不要照搬旧教程中“调用 create_deep_agent 一定默认有 write_todos”的说法。

**Todo 状态是模型管理的工作清单，不是业务验收事实。** 模型把一项改成 completed，不证明它真的调用了证据工具，更不证明外部写入已经成功。

### 4.3 如何工程化

- 稳定的必经业务阶段由代码约束。
- 模糊研究部分允许模型规划。
- 每项完成需对应证据或程序检查。
- 计划失败后可以重规划，但不能无限追加任务逃避终止。
- 总预算包括规划、子任务、工具、重试和汇总。

## 5. 文件系统与 Backend：上下文可以放到哪里

### 5.1 为什么需要文件

模型上下文不是无限容量。大量原文、搜索结果和中间报告可以放进工作文件，模型只保留索引、摘要和当前需要的片段。这样减少每轮重复传输，但可能增加检索和文件读取的轮数。

写到文件不等于模型忘记了已进入历史的内容，也不等于安全脱敏。读取文件的内容仍会进入后续模型上下文。

### 5.2 Backend 类型

| Backend | 数据位置 / 作用 | 生命周期 | 风险与边界 |
| --- | --- | --- | --- |
| `StateBackend` | 文件存在图 State | 跟随 thread 状态及检查点 | 不是默认落到本机同名路径 |
| `StoreBackend` | 文件映射到 Store 命名空间 | 可跨 thread；是否跨进程取决于 Store | 必须隔离租户、用户和版本 |
| `FilesystemBackend` | 映射真实文件系统 | 跟随宿主存储 | 需严格目录边界；不自动构成 OS 沙箱 |
| `CompositeBackend` | 按路径前缀路由到多个 Backend | 各后端不同 | 路由和 namespace 不能由模型任意扩权 |
| Sandbox 类 Backend | 在具备执行隔离的环境工作 | 取决于具体实现 | 隔离强度、网络、秘密、资源限额须单独验证 |

`execute` 是否真正可用取决于 Backend 是否实现相应执行协议。工具名字出现在列表里，不代表 StateBackend 能执行任意 shell。

### 5.3 Composite 的典型划分

临时证据走 State；允许长期保存的规则走租户隔离 Store；可信审阅后的输入目录可以只读映射。不要把持久化路径当作授权：能路由到某个 Backend，不意味着当前用户有权读写。

仓库示例把 `/memories/` 路由到 Store。组合层会处理路径前缀，Store 内部 key 未必仍保留相同完整前缀，排查时要分清虚拟路径和真实 key。

## 6. Skills：可发现的任务方法，不是权限插件

### 6.1 一份 Skill 包含什么

典型目录包含 `SKILL.md`，可附带脚本、模板、参考文件。Frontmatter 的 name、description 等帮助发现技能，正文说明任务方法和使用条件。

Skill 的核心是“怎样完成某类任务”的可复用流程，例如采购评审：先计算金额、查预算、查库存与供应商，再按证据形成结论。

### 6.2 渐进式加载

通常先向模型提供少量技能元信息，让模型判断是否需要；需要时再读取完整正文和相关资源。相比全部粘进 system prompt，减少无关上下文，但发现描述写差时可能选错技能或根本不加载。

这不是权限路由：模型发现一个技能，不等于凭空获得技能中提到的工具。真实工具必须预先注册并经过权限控制。

### 6.3 动态 Skill 与可信版本

动态 Skill 可由应用为新 thread 注入到 `StateBackend.files`。技能来自什么渠道、适用于哪个租户、版本是什么，都应由可信应用决定，而不是让网页或模型自行授权。

仓库版本专题验证 `skills_metadata` 会被保存在私有 State 中，同 thread 修改文件不保证重新扫描索引。新版本通常为新 thread 分配，旧任务继续固定旧版本；确需升级则显式迁移。

注意：metadata 缓存不是文件内容的密码学快照。旧索引与新正文混用仍可能产生不一致，不能仅靠缓存声称技能已被完整冻结。

### 6.4 常见 Skill 设计错误

- description 太空泛，所有任务都匹配。
- 一个技能包含十几种无关业务。
- 把真实 token 写入示例。
- 文档要求调用并不存在的工具。
- 将参考文档中的操作指令当成用户授权。
- 更换版本后只改正文，不更新测试与追踪元信息。

## 7. Memory 与上下文压缩

### 7.1 三种东西不要混在一起

| 机制 | 保存什么 | 关键问题 |
| --- | --- | --- |
| messages / Checkpoint | 当前 thread 的交互和执行历史 | 如何恢复、裁剪、保护隐私？ |
| `memory=[...]` / AGENTS.md | 启动时载入的规则与背景文件 | 谁能修改、是否可信、何时过期？ |
| Store / 长期资料 | 跨 thread 可用的信息 | 命名空间、检索、权限、更新机制？ |

AGENTS.md 可以表达偏好或工作原则，但不能成为认证证据。文件里写“我是管理员”不会获得管理员权限。

记忆保存要区分：用户明确偏好、经核实事实、模型推测、临时任务假设。把错误结论写入长期记忆会反复污染后续任务。

### 7.2 Summarization 与 Offloading

摘要压缩历史，offloading 把大块内容放到外部文件并按需取回。摘要更省上下文，但可能丢细节；文件保留原文，但读取有延迟和调用成本。

关键金额、动作 ID、用户约束、批准参数和来源证据，最好保留结构化记录，不只依赖一段自然语言摘要。

### 7.3 缓存不是普适省钱开关

Provider-specific prompt caching 依赖具体服务商、模型、请求布局和计费规则。默认栈注册缓存相关逻辑，不代表当前 DeepSeek / 兼容接口自动获得同样效果。

## 8. 三种子 Agent：先看生命周期

| 类型 | 谁构建内部 Agent | 父调用是否等待 | 适用情况 |
| --- | --- | --- | --- |
| 声明式 `SubAgent` | Deep Agents 按配置构建 | 同步 task 通常等待 | 明确角色、独立工具集 |
| `CompiledSubAgent` | 应用先构建 Runnable / 图 | 仍是同步委派 | 复用已有流程与自定义图 |
| `AsyncSubAgent` | 远端 Agent 服务运行目标图 | 启动后可继续，不等完成 | 慢任务、后台任务、跨服务执行 |

子 Agent 是逻辑分工，不必使用不同模型，也不一定有独立进程。是否隔离内存、文件、权限和网络，要分别检查。

### 8.1 声明式 SubAgent：任务描述就是输入

父模型通常通过 `task(description=..., subagent_type=...)` 委派。description 应带任务目标、已知事实、范围、输出格式和完成条件，不能只写“帮我看看”。

默认 isolated 主要隔离对话：重建子 messages，不把父完整对话直接交给子 Agent。但兼容 schema 接受的公共业务 State 仍可能传播，所以“isolated＝任何父数据都绝不传入”是错误的。

子任务完成后，父级通常拿到最终结果形成的 ToolMessage，而不是完整子对话。允许的公共 State 可通过 reducer 回传；todos、私有字段等有过滤规则。

### 8.2 Fork：继承更多上下文的代价

fork 模式继承更多父对话与提示，适合确实依赖完整会话的任务。代价是 token 更多、信息暴露面更大、父子角色可能冲突。

仓库专题将其视为实验性能力，特定版本对嵌套 fork、技能定义等有限制。不要把它当作廉价的进程 fork，也不要把所有继承字段规则推广到其他版本。

### 8.3 CompiledSubAgent：编译不等于后台

它接收应用已构建的 Runnable / 图；不会自动重写其模型、工具和 Middleware。当前仓库契约要求返回包含兼容 `messages` 的状态，可优先利用 `structured_response` 形成父级结果。

因此复用一个只返回 `{"answer": ...}` 的图可能需要适配契约。构建成功不证明调用结果符合要求，必须测输入输出。

### 8.4 AsyncSubAgent：两套执行历史

当前仓库通过 Agent Protocol / SDK 管理远程 thread 与 run，父 State 中的 `async_tasks` 记录追踪信息，而非远程完整执行状态。

需要分别理解 start、check、update、cancel、list：

- start 创建远程任务，返回 tracking ID。
- check 查询当前状态，查询失败不等于任务失败。
- update 可以在同一远程 thread 上创建新 run，而不是修改旧 run 的 Python 栈。
- cancel 请求取消，不代表已执行副作用回滚。
- list / 缓存状态可能滞后，必要时刷新。

不要在父模型里无间隔循环 check。使用应用调度、事件回调或有退避的查询，并处理父级重启后的追踪恢复。

## 9. 带中文注释的构建片段

此片段只定义纯内存证据工具并构造 Agent，不创建真实模型客户端、不调用 `invoke`。调用方必须自行提供已配置的模型；这里不是生产权限方案。

```python
from deepagents import create_deep_agent
from deepagents.backends import StateBackend
from langchain.agents.middleware import TodoListMiddleware
from langchain_core.tools import tool


@tool
def read_demo_budget() -> dict[str, int]:
    """返回固定的虚构预算事实，不查询数据库或外部接口。"""
    return {"total_yuan": 272000, "budget_yuan": 268000, "gap_yuan": 4000}


def build_review_agent(model):
    # isolated 子 Agent 只接收明确委托，不依赖父对话中的隐含背景。
    reviewer = {
        "name": "budget-reviewer",
        "description": "核对预算事实，给出金额和证据，不执行业务写入。",
        "system_prompt": "调用预算工具，区分工具事实与建议，缺少证据时明确说明。",
        "tools": [read_demo_budget],
        "mode": "isolated",
    }
    return create_deep_agent(
        model=model,
        backend=StateBackend(),
        subagents=[reviewer],
        # 本仓库版本需显式加入 Todo 中间件，不能假定默认存在 write_todos。
        middleware=[TodoListMiddleware()],
        system_prompt="复杂任务先规划；预算问题委派专家，最终只按证据总结。",
    )
```

这里仍可能有默认文件工具和 general-purpose 子 Agent，不能仅凭自定义列表声称最小工具白名单已经完成；最小权限需进一步配置并检查实际注册工具。

## 10. Middleware、工具重试与结构化输出

Middleware 可在 Agent、模型、工具生命周期中观察、修改或包裹行为。适合重试、审计、动态工具过滤、上下文控制等横切逻辑。

当前 0.7.x 支持按 Middleware 名称匹配替换默认实例。替换不是合并所有配置：自定义 FilesystemMiddleware 需要自己正确设置 backend、权限等，不能指望顶层参数自动重新灌入替换实例。

工具重试要区分两层：

1. 模型重新提出工具调用：会产生新的决策轮次。
2. Middleware 对同一次工具调用内部重试：模型可能只看到最终结果。

仓库 `ToolRetryMiddleware(max_retries=2)` 表示初次调用之外最多再试两次，不是总共两次。不要对权限错误、业务不合法或未知写入结果套用统一重试。

`response_format` 可约束输出结构；不是本仓库每个专题都已经使用或测试的能力。结构化字段正确仍不保证建议、金额和来源正确，应单独做业务验收。

## 11. 权限、人工审批与执行环境

三层控制不可互相替代：

- Prompt / Skill：告诉模型应如何做。
- 工具与应用：实际校验身份、租户、参数、预算和动作范围。
- 执行环境：限制文件路径、网络、进程与资源。

`interrupt_on` 可在指定工具执行前进入人工审批，恢复依赖 checkpointer 与相同 thread。approve、edit、reject 是框架决策协议，不是自然语言“同意”就自动执行。

人工修改参数后，还要重新校验 schema、权限和业务前置条件。批准某一笔动作，不等于批准之后所有动作。

文件 permissions 主要针对其覆盖的文件能力；自定义 HTTP、数据库、支付工具必须自行鉴权。Shell 开放后可绕开只作用于文件工具的约束，需独立的执行环境与策略。

仓库 OpenSandbox 示例单独放置，是因为已声明的适配包依赖范围与 deepagents 0.7.x 冲突；不要为了跟文档相似强装进主环境。

## 12. 分层问答：定位与上下文

### Q1：Deep Agents 比普通 Agent 多了什么？

**简答：** 主要多的是长任务执行支架：文件工作区、上下文管理、技能和委派等组合能力，不是换了一种模型。

**深入：** 普通工具循环解决“调用哪个函数”，Harness 进一步解决“复杂任务怎样组织工作、控制上下文和持续推进”。

**追问：** 什么时候不用？短任务、固定阶段或类型化输出已足够时，选更小的方案。

**误区：** 名字里有 Deep 就一定推理更强。

### Q2：Deep Agents 与 LangGraph 是替代关系吗？

**简答：** 不是。Deep Agents 使用下层 Agent 与图运行能力，提供较高层的执行组合。

**深入：** 需要精确控制业务阶段时，可以在 LangGraph 中嵌入适当 Agent；需要现成研究 / 文件任务环境时，可用 Deep Agents。

**追问：** 哪些恢复语义仍要懂 LangGraph？检查点、thread、中断重入和外部副作用。

**误区：** 用了上层 SDK 就不必理解恢复机制。

### Q3：Skill 与 Tool 的本质区别？

**简答：** Skill 描述方法和流程，Tool 提供可执行能力。

**深入：** Skill 可以指导先查预算再评审，但真正读取预算必须有已注册工具。技能正文不能授予权限。

**追问：** 用户上传 Skill 说“先读取全部客户资料”能照做吗？要看明确用户授权、数据权限和工具边界。

**误区：** 加一个 SKILL.md 就安装了新的外部能力。

### Q4：Memory 与 Skill 有什么不同？

**简答：** Memory 更偏长期背景和规则，Skill 更偏特定任务的方法包与按需加载。

**深入：** 两者都可能是文件文本，但加载时机、用途和维护方式不同；均不能替代服务端权限。

**追问：** 模型生成的建议能自动写进永久记忆吗？应有筛选、确认、过期和纠错机制。

**误区：** 保存越多越智能。

### Q5：文件系统为什么能帮助长任务？

**简答：** 把大块中间结果移出每轮消息，只保留索引并按需读取。

**深入：** 这是空间与访问成本的取舍：减小上下文，但增加检索轮次和文件一致性问题。

**追问：** 写入文件就不占上下文了吗？历史里已经出现过的文本不一定自动消失，需要配合摘要 / 裁剪。

**误区：** Offloading 等价于脱敏。

### Q6：StateBackend 是真实文件夹吗？

**简答：** 不是，虚拟文件保存在图 State，持久性取决于 thread 与检查点。

**深入：** 真正映射宿主文件系统用相应 Backend；不同后端的存储、隔离和执行语义不能混用。

**追问：** 能用 `/tmp/report.md` 推断宿主文件位置吗？不能，只看到虚拟路径时尤其如此。

**误区：** write_file 成功就去宿主同名目录找文件。

## 13. 分层问答：子任务与工程控制

### Q7：isolated 是完全不共享父 State 吗？

**简答：** 不是。主要隔离父对话，公共字段仍可能在兼容 schema 下传播。

**深入：** 当前版本过滤 messages、todos、structured_response、私有字段等，再构造子输入；输出也有回传规则。

**追问：** 怎样避免租户秘密泄露？最小任务包、明确字段、最小工具与运行时权限，而非只依赖 isolated 名称。

**误区：** isolated 是进程级安全沙箱。

### Q8：CompiledSubAgent 为什么还会等待？

**简答：** Compiled 描述构建方式，不描述后台运行；它仍通过同步 task 委派。

**深入：** 复用的是已编译 Runnable，其输入输出契约、工具和 Middleware 应由应用保证。

**追问：** 只返回 answer 字段为何失败？本版本要求兼容 messages 状态契约。

**误区：** 编译后的子 Agent 自动常驻后台。

### Q9：AsyncSubAgent 与 async def 有何不同？

**简答：** async def 是 Python 非阻塞编程方式；AsyncSubAgent 是远程后台任务协议与生命周期。

**深入：** 后者有独立 thread、run、追踪 ID、查询和取消，父级与远程各自持久化。

**追问：** 父进程退出，远程一定取消吗？不能假定，必须按远程协议管理。

**误区：** await 同步 task 就实现了后台委派。

### Q10：为什么要显式加 TodoListMiddleware？

**简答：** 本仓库 0.7.x 默认栈不自动添加它，版本行为需要核对。

**深入：** 名称和宣传能力不能代替实际工具注册检查；规划是否出现取决于配置与模型行为。

**追问：** todos 全部 completed 能验收吗？不能，仍要核对动作和证据。

**误区：** 所有版本默认工具都完全一样。

### Q11：子 Agent 越多是否越准确？

**简答：** 不一定。它增加上下文隔离和专业分工，也增加协调成本和错误传播。

**深入：** 任务独立且可并行时可能有收益；强依赖任务、多次重复检索、不同口径容易降低效果。

**追问：** 怎样证明拆分有收益？与单 Agent 在同一评估集上比较成功率、延迟、成本和人工接管率。

**误区：** 三个 Agent 赞同就是真实。

### Q12：Middleware 返回错误文本后，任务是否就安全了？

**简答：** 只代表模型得到了失败信息，不保证它不会误读或编造补齐。

**深入：** 工具结果要显式区分 success / unavailable / denied / unknown；关键证据缺失时验收必须拒绝。

**追问：** 服务不可用返回空库存合适吗？不合适，未知不能当作零。

**误区：** 没抛异常就能继续成功。

### Q13：技能热更新为什么没有生效？

**简答：** 当前 thread 可能复用技能 metadata，文件变化不意味着重新扫描和重新加载。

**深入：** 检查 thread、Backend、路径、缓存和实际正文版本；新任务固定新版本，老任务不要悄悄改语义。

**追问：** metadata 里写 v1 就能证明正文是 v1 吗？不能，需要版本内容一致性和发布约束。

**误区：** 运行时覆盖文件是无风险升级。

### Q14：有文件 permissions，还需要 Sandbox 吗？

**简答：** 要看是否开放 shell、网络及其他工具；文件规则不覆盖所有通道。

**深入：** 需要独立限制路径、网络出口、资源与秘密注入；审批只解决是否允许某次动作，不提供进程隔离。

**追问：** 本地 shell 可以被称为安全沙箱吗？不能仅凭名称这样说。

**误区：** Prompt 写“不要访问其他目录”就完成隔离。

### Q15：怎么证明一个 Deep Agent 完成了任务？

**简答：** 验证必需工具证据、结果范围、金额、来源和真实副作用状态，不只看最终文本。

**深入：** 规划清单、模型总结与外部验收分别记录；对缺失证据、冲突和服务不可用明确失败或部分完成。

**追问：** 结构化输出已经过 Pydantic 呢？只证明结构满足约束，事实还要核对。

**误区：** completed Todo＋最终中文总结＝任务成功。

## 14. 场景题：怎样设计采购评审 Agent

### 14.1 先定义输入与不变量

输入：可信租户身份、采购对象、数量、单价、供应商与评审范围。
不变量：金额由确定性工具计算；缺少预算证据不能批准；未经批准不能锁定预算；每份建议能追溯来源。

### 14.2 再划分角色

父 Agent 管目标与汇总；预算专家查预算；风险专家查供应商与库存。可并行的证据分开，不要让子 Agent 反复重复计算同一金额。

委托必须带完整任务包；公共 State 用有 ID 的证据结构，不用几段含糊自然语言互相覆盖。

### 14.3 最后考虑失败与恢复

供应商查询超时可有限重试；预算权限不足直接停止。子任务失败保留已有证据但不伪造完整结论。审批后外部执行使用幂等键，重启后依检查点恢复并先核对业务状态。

面试加分点：明确区分“评审建议”与“执行批准”，承认 mock 例子没有证明生产写入和长期持久化。

## 18. 高级追问：Harness 内部到底发生了什么

这部分把“配置了某能力”进一步拆成：构建时装配什么、运行时传播什么、失败时留下什么。源码行为以 0.7.15 及仓库 LangChain 1.4.1 为边界；生产补强方案另行标注。

速查：Middleware 装配看 H1–H2；父子状态与契约看 H3–H5；技能发布与供应链看 H6–H7；文件、压缩看 H8–H9；远程故障与总体验收看 H10–H11。第 19 节适合练跨层故障定位。

<a id="da-middleware"></a>

### H1：Middleware 都配上了，顺序为什么仍能改变安全和重试结果？

**第一问：** `auth、cache、retry` 三个 wrapper 怎样执行？当前 LangChain 的 wrap 组合以列表中前者为外层，可理解为请求 `auth→cache→retry→tool`，响应反向返回。此规则针对 wrap hook，不能据此推断所有 before / after hook 的顺序。

**追问一：cache 在 auth 外层有什么风险？** 缓存可直接返回结果而不进入内层；如果授权只在内层做，命中可能绕过重新鉴权。缓存 key 带租户只能解决一部分串租户问题，权限撤销与对象版本变化仍要处理。

**追问二：audit 在 retry 外层还是内层？** 外层易记录一次逻辑调用，内层易记录每次尝试。两者都合理，但指标应分别有 logical_call_id、attempt、最终状态。外层只记“成功”会隐藏反复失败，内层每次都算一个业务动作又会夸大调用量。

**追问三：审批放外层后，retry 能重复写入吗？** 可能。一份批准只说明允许该动作，不让重复执行变安全。内部重试仍需稳定动作 ID、幂等与未知结果核对。

**验证方法：** 用只向内存列表追加标签的 wrapper 替身，断言进入 / 退出顺序、短路行为、重试次数、异常传播，再检查生产注册栈。不要仅凭配置列表注释判断。

### H2：同名 Middleware 替换，为什么会把原来的安全配置弄丢？

**第一问：** 自定义实例与默认实例 `.name` 相同，会发生什么？当前 `_apply_custom_middleware` 按名称在原槽位替换实例，不是把新旧参数逐项深合并。

**追问一：顶层传了 backend、permissions，新实例一定继承吗？** 不能这样假设。实例替换后，需要对照构建源码确认哪些配置由它自己持有、哪些确实由外层统一执行。尤其自建 FilesystemMiddleware 不应靠“顶层写过一次”推断配置仍然完整。

**追问二：新名字的实例又放哪里？** 当前逻辑可把新增实例放在核心栈之后、部分 profile / caching / memory 尾部之前；并不是所有自定义实例简单追加到最后。还有工具排除等后处理，最终顺序应看装配结果。

**追问三：升级怎么防回归？** 记录并测试实际 middleware 名称、工具 schema、后端、权限拒绝行为，而不只对构造参数做快照。依赖升级可能改变默认栈，即使应用代码没变。

**反例：** “自定义了同名文件中间件，只改提示词，其他配置肯定沿用。”这是对象替换和配置合并混淆，不是模型不听话。

### H3：isolated 隔离了什么，没隔离什么？

**第一问：** 父 State 有 `messages、tenant_hint、files`，子 Agent 都看不到吗？不是。当前 isolated 会重建 messages，以委托描述作为子对话；符合传播规则和子 schema 的公共业务字段仍可能进入子任务。

**追问一：那私有字段怎样处理？** 当前实现过滤 messages、todos、structured_response 等特定字段及标记的私有状态；声明式 fork 又有不同继承路径。不能把一次 isolated 实验推广成所有 mode、所有 schema、所有工具都隔离。

**追问二：父级持有管理员 HTTP 客户端，子级只有只读提示词，安全吗？** 不安全。依赖对象、Backend、工具与网络权限必须实际限制。逻辑对话隔离不是 OS 进程隔离，也不是能力降权。

**追问三：怎样让隔离可检查？** 明确子任务输入白名单、独立工具集和命名空间；用哨兵字段验证哪些可见。测试父消息不出现只是第一层，还要测共享文件、Store、自定义 State 和工具返回是否泄露。

**答题要点：** 上下文隔离、状态隔离、资源隔离、权限隔离四个词要分别解释。

### H4：为什么子 Agent 返回后父 State 会重复追加旧结果？

**第一问：** 子图返回完整 evidence 列表，父字段用拼接 reducer，会怎样？如果把已有证据也作为更新回传，父级可能再次拼接。完整状态视图与增量协议不一致，是常见原因。

**追问一：框架会自动只回最终文本吗？** 当前 task 返回不仅可生成父 ToolMessage，还可传播未被排除的公共 State 更新。不要把“父只看到子总结”误解为其他 channel 永不变化。

**追问二：怎么修契约而不是补提示词？** 为共享字段定义更新语义；用稳定证据 ID、明确版本的 reducer，或由适配器只返回允许的增量。父、子以及聚合者必须使用同一口径；不能一边返回快照，一边按事件追加。

**追问三：两个专家给同一预算不同值呢？** 记录来源、时点与版本，按业务规则解决或报冲突。不要按“最后返回”“更长的答案”或多数票选事实。

**验证方法：** 父先有一条证据，再并行调用两个子任务；检查父旧记录不被重复、不被静默覆盖，缺失 / 冲突状态可追踪。

### H5：CompiledSubAgent 复用已有图，最容易踩什么契约问题？

**第一问：** 把只返回 `answer` 的 Runnable 塞进去，为什么构造能成功、调用却失败？当前回传路径要求结果包含 `messages`；类型或构建检查不能替你执行所有运行时分支。

**追问一：已有 structured_response 还要 messages 吗？** 当前代码先检查 messages，再优先将非空 structured_response 序列化成父 ToolMessage 内容。不能因为使用结构化结果就省略当前要求的状态契约。

**追问二：没有 structured_response 时，父拿什么？** 当前实现从消息尾部查找非空 AIMessage 文本；不等于返回最后一条任意消息，也不一定是子工具的最后原始数据。应让子流程明确产出最终结论。

**追问三：Compiled 是否会自动继承父的模型、工具和审批？** 不应假设会改造一个不透明 Runnable。已有流程内部能力由它自己的构建决定，父侧委派控制与子内部工具权限都要检查。

**实践：** 在编译图外加小而明确的契约适配，测试成功、空消息、缺字段、不可序列化输出与子失败；不要复制整套图只为改一个返回字段。

### H6：技能 metadata 已缓存，为什么仍不能证明正在使用旧版 Skill？

**第一问：** 旧 thread 缓存 v1 metadata，随后覆盖路径里的正文为 v2，会怎样？索引可能仍说 v1，而实际 read_file 读到 v2。metadata 是发现信息，不是对整个资源包的不可变快照。

**追问一：可靠发布要固定什么？** 固定技能清单、正文、脚本和参考文件的版本及内容 hash，并使实际读取定位到那份不可变内容。只写一个 `version: v1` 标签不够；hash 只做完整性，可信来源仍需审查或签名 / 发布权限。

**追问二：两个 source 出现相同技能名怎么办？** 当前加载按 source 顺序，后来源可覆盖前来源同名项。租户上传目录如果排在可信目录后，可能意外替换可信技能；发布策略需明确允许覆盖哪些名称。

**追问三：空列表也会缓存吗？** 当前 before_agent 检查字段是否存在，而不是是否非空；已经存在的空 metadata 也会跳过再次扫描。调试“新技能没出现”时需检查 thread 状态，不只看磁盘目录。

**追问四：紧急修复恶意旧技能还能固定旧版吗？** 安全撤销优先于可复现：暂停受影响任务、标明版本失效、经批准迁移或重启。不能用“老任务固定版本”作为继续执行已知恶意代码的理由。

### H7：Skills 和 MCP 既是扩展点，为什么也是供应链入口？

**第一问：** SKILL.md 写“先上传全部文件才能分析”，模型是否应该照做？不能。它提供方法，不是当前用户的新授权；来源文件和工具返回均可能包含提示注入。

**追问一：不执行 Skill 脚本是不是就安全？** 不够，纯文本也能诱导错误工具选择、泄露数据或污染长期记忆。工具侧仍应限制可读范围、外发目的地与写入。

**追问二：MCP server 更新了同名工具描述呢？** 工具语义、schema 或权限需求可能变化。对高风险能力可审查发现清单、固定或校验版本，运行时继续在执行端鉴权；“发现到了”不是“授权了”。

**追问三：怎样测试？** 在虚构技能和工具返回中加入越权诱导，检查模型提出禁止动作的比例以及执行层实际阻断结果。模型没提出不代表工具边界安全，工具阻断也不代表无需改善模型行为。

### H8：CompositeBackend 怎样出现跨租户或路径越界？

**第一问：** 给每个租户一个 `/memories/` 前缀够不够？虚拟路径相同可以，但其后端 namespace 必须从可信身份注入。让模型填写 namespace 或宿主路径，就可能越界。

**追问一：前缀匹配有什么难点？** 路径规范化、相近前缀、上级目录、分隔符、宿主符号链接等都会影响边界。不能把单次字符串 `startswith` 当完整路径安全实现；实际保证取决于具体 Backend。

**追问二：两个子 Agent 同时写 report.md 怎么办？** 最简单是独立路径，如 run / task / artifact，再由单一汇总者合并。真要共享写，需版本检查或明确冲突协议，不能期待文件系统替自然语言段落合并。

**追问三：StateBackend 有 checkpointer 就一定永久保存吗？** 仍看 saver 和生命周期。StoreBackend 能跨 thread 也不等于跨进程可靠；文件语义、存储耐久性与访问权限要分别验收。

**实践边界：** 本文给的是审查要点，不声称当前某 Backend 存在具体漏洞，也没有运行宿主文件安全实验。

### H9：上下文压缩后，Agent 为什么“忘了不能做什么”？

**第一问：** 摘要保留任务结果，却遗漏“不得导出”与证据时点，会怎样？后续决策可能按不完整上下文工作。摘要不是无损压缩，模型也可能把假设写成事实。

**追问一：关键内容放在哪里？** 权限与禁止动作在可信策略和工具层强制；任务范围、提案版本、动作 ID、证据索引存结构化状态；摘要帮助理解，不是唯一事实账本。

**追问二：原文已 offload，随时读回来就行吗？** 需要知道文件在哪、对应哪个版本、哪些段落支持哪些结论。没有索引的文件堆会增加盲读、重复读取和丢证据风险。

**追问三：怎样衡量是否值得压缩？** 比较总输入 token、额外读文件轮数、延迟与任务验收率。还要测试摘要丢失关键信息时系统是否停止 / 补读，而不是只比较摘要字符数。

**反例：** “只剩 10% 上下文，所以成本下降 90%。”忽略后续回读、重试与质量下降，是不成立的工程结论。

### H10：AsyncSubAgent 启动返回失败，为什么不能直接再启动一次？

当前启动路径会创建远程 thread、创建 run，再向父 State 写 tracking。三个阶段并非跨服务原子提交。

| 故障位置 | 可能的远程状态 | 父侧该如何理解 |
| --- | --- | --- |
| 创建 thread 前失败 | 可能未创建 | 仍需结合错误阶段判定 |
| thread 成功、run 创建失败 | 可能留下空 thread | 不是完整任务已执行 |
| run 已创建、响应丢失 | 远程可能正在执行 | 不应按“肯定没启动”重发 |
| run 已创建、父 tracking 未保存 | 远程任务失联 | 存在孤儿任务与重复启动风险 |

**追问一：父有 checkpointer 不就能恢复吗？** 父只能恢复已保存 tracking，不能恢复从未记录下来的远程 ID；远程 checkpoint 也不自动变成父的事务。

**追问二：怎么补强？** 应用可引入稳定委托 ID、启动登记与远程查询 / 去重能力，定期核对孤儿任务；前提是远端支持相应关联。不能把这些建议说成当前 start 工具已经全部实现。

**追问三：cancel 与 update 竞争呢？** 每次操作应明确目标 run_id、任务版本和预期状态，避免取消旧 run 后误以为新 run 也停了。查询缓存可能滞后；cancel 请求成功也不撤销已完成副作用。

**追问四：适合所有子任务吗？** 不适合。短任务引入远程生命周期增加复杂度；只在跨服务、长耗时或独立运行确有收益时使用。

### H11：Todo 完成、所有子 Agent 成功，为什么父任务还可能不合格？

**第一问：** 每个专家都回答了，为什么不能直接汇总？局部输出可能使用不同币种、时间范围或对象版本；“各自成功”不保证满足同一个全局契约。

**追问一：怎样避免局部最优？** 委托包固定共同定义、输入事实、范围和证据格式，父级做跨结果一致性检查。子任务不得自行把“缺失信息”改成“默认通过”。

**追问二：预算如何控制？** 父级给出总预算，并对子任务预留额度、限制并发和递归深度。不能父给三份子预算，每个子再独立生出三份同额预算；纯文字“最多花十元”也不是硬限制。

**追问三：某专家失败能降级吗？** 在任务契约预先允许时可部分完成，清楚标记结论范围。关键资格或必需证据缺失时应拒绝完整成功，不让汇总模型润色掉失败。

## 19. 复杂场景：升级技能后，隔夜采购评审恢复出错

**题目：** 昨天一份评审任务已完成预算子任务并等待人工；今天升级 Skill 和文件 Middleware 后恢复，出现预算重复、技能规则不一致，还多启动一个远程任务。如何排查？

### 19.1 先止损，再分层定位

先暂停新的自动外部执行，保留 thread、版本与远程任务关联；不通过清空 State、删除记忆或换 thread 来“修复”，因为这会丢失追踪并可能重做业务动作。

分四条线检查：

1. **预算重复：** 看子图返回的是快照还是增量，公共 State 传播了哪些字段，父 reducer 是否追加了旧 evidence；不要首先怪模型重复回答。
2. **规则混用：** 看 skill metadata、实际正文与资源包 hash 是否一致，是否是旧 thread 缓存索引＋新路径内容。完整定位需要旧版本发布记录，标签不够。
3. **权限变化：** 看同名 Middleware 是否替换实例、backend / permissions 是否仍配置，最终实际工具集是否发生变化。
4. **远程重复：** 区分 start 重放、响应丢失和 tracking 未保存；核对原远程 run，不能把父侧启动报错等同于远程未创建。

### 19.2 可接受的修复决策

对旧任务优先使用匹配的代码与不可变技能包恢复；确需升级则显式迁移提案与证据，旧审批不适用的新语义必须重新确认。共享字段修正增量契约或使用有版本合并；远程任务依据实际状态选择继续、取消或人工核对。

**面试官问：“重建一个 Agent 不就干净了吗？”** Agent 配置对象重建不等于业务世界重置；旧任务、文件与远程动作可能仍然存在。重启是实施手段，首先要保全动作身份和恢复协议。

**面试官问：“能保证以后绝不重复吗？”** 需要限定层次：本地合并可防重复事件，远程启动需要远端幂等支持，业务动作仍需服务端去重；不能拿一个 reducer 保证整个分布式链路。

## 21. 白板演练：让抽象的 Harness 能力变得可推算

### W1：缓存命中时，鉴权和审计到底执行几次？

有四个概念性工具 wrapper，先后为 `audit、auth、cache、retry`，前者在外。retry 仅重试可重试异常，最多额外尝试一次；暂不考虑其他默认 Middleware。

请分别推演：首次调用缓存未命中、工具第一次临时失败第二次成功；下一次同 key 缓存命中；下一次权限撤销但缓存仍存在。不要只回答“取决于顺序”，请写执行轨迹。

<details>
<summary>参考轨迹、计数与反例</summary>

第一次可以表示为：

```text
audit.enter
  auth.check → allowed
    cache.lookup → miss
      retry.attempt.1 → tool → temporary_error
      retry.attempt.2 → tool → success
    cache.save
audit.exit → logical_success
```

第二次：audit 进入，auth 仍检查，cache 命中后返回，retry 与 tool 不进入。第三次：audit 进入，auth 拒绝，cache 不进入，即使旧缓存还在也不应读取它来绕过授权。

| 场景 | 逻辑调用数 | auth 次数 | 原工具尝试数 |
| --- | --- | --- | --- |
| 首次未命中、一次重试 | 1 | 1 | 2 |
| 授权有效、命中缓存 | 1 | 1 | 0 |
| 权限已撤销 | 1 | 1 | 0 |

这里假设 audit 用正确的 finally / 异常记录方式保留拒绝与失败；只有进入函数时记一条日志，不等于完整审计。内部两次尝试还需单独指标，不能从一次 logical_success 推断只触及工具一次。

追问变体：cache 放在 auth 外会不会绕过检查？可能。retry 放在 audit 外，可能重复产生多次逻辑审计；audit 放 retry 内则常记录每次尝试。没有唯一正确顺序，但每一层保证必须有明确含义。

评分：轨迹准确 2 分；区分逻辑调用与尝试 1 分；命中时仍鉴权 1 分；说明只是假设栈、不是完整默认栈 1 分。

</details>

### W2：isolated 的子任务，为什么仍可能读到不应读取的资料？

父任务拥有完整会话、公共 evidence 字段、共享工作区、管理员能力客户端。子 Agent 配置 isolated，system prompt 写“只读当前采购单”，但工具闭包捕获了父客户端。

请按四种隔离分别判断：对话、State、文件 / Store、实际工具权限。不要用一个 isolated 单词回答全部。

<details>
<summary>参考隔离矩阵</summary>

| 边界 | 当前题目能推断什么 | 还必须检查什么 |
| --- | --- | --- |
| 对话 | isolated 会重建子 messages | 委托描述是否又复制了敏感父内容 |
| State | 部分公共字段仍可能传播 | 实际 schema、过滤规则、回传 reducer |
| 文件 / Store | 不能由消息隔离推断资源隔离 | Backend、路径、namespace、宿主能力 |
| 工具权限 | 提示词不改变客户端能力 | 凭据权限、租户过滤、服务端鉴权 |

最直接的风险是工具仍以管理员能力访问。合适的改法是给子任务提供受限服务接口 / 凭据与可信范围，而不是只加强 prompt。任务包只传必需证据 ID 和明确事实，文件按 task 隔离，返回值按契约接收。

额外追问：“子工具是只读就没有问题？”只读也可能读过量、跨租户或将内容发送给模型。影响不止业务写入。

评分看是否能指出所有数据路径；只证明父消息没出现，不足以证明安全隔离。

</details>

### W3：Offloading 少了很多 token，为什么总费用反而上升？

简化题：一块 24,000 token 的原文，在后面六次请求中被原样重复携带。方案 B 改为每次携带 1,000 token 索引，并累计补读 8,000 token 原文。先比较这块内容的传输量，再解释哪些假设在真实运行里可能不成立。

<details>
<summary>参考计算与测量口径</summary>

在题设假设下，A 的重复输入为 `24,000×6=144,000` token，B 为 `1,000×6+8,000=14,000` token。这只比较被替换的那块输入，不是整个 run 总 token，更不是账单直接降低同样比例。

实际可能出现：补读内容进入历史后继续每轮携带；索引描述不清导致反复读文件；生成摘要本身收费；任务分裂产生更多子调用；Provider 对重复前缀有不同缓存计价；压缩遗漏信息导致失败重跑。

因此应测总输入 / 输出 token、缓存用量、文件读取次数、调用轮数、延迟、验收率和每成功任务成本，并固定相同任务范围。不能只对比单次 prompt 字数。

进一步追问：“是不是应该全部只留摘要？”不是。适合保留结构化关键事实＋可回源索引＋按需原文，具体见下一节。压缩必须保留修正错误的途径。

</details>

## 22. 工件协议：为什么报告文件不能只是一段自由文本？

### 22.1 用 manifest 连接委托、证据与结论

父级收到“报告已生成”时，需要知道它属于哪个任务、适用哪些范围、证据缺什么、引用哪个文件版本。应用可定义如下工件描述；它是通用协议示例，不是 Deep Agents 内置字段格式：

```json
{
  "task_id": "demo-review-budget",
  "scope_version": 2,
  "status": "partial",
  "artifact": {
    "path": "/runs/demo/tasks/budget/report.json",
    "content_hash": "<由应用计算的完整性摘要>",
    "schema_version": 1
  },
  "evidence_ids": ["demo-budget-v3"],
  "missing": ["尚未核实供应商资格"],
  "allowed_use": "仅形成建议，不作为执行批准"
}
```

manifest 与报告应由可信应用验证，而不是模型写了 content_hash 就算验证。Hash 可检测是否换了内容，不证明内容真实，也不等于访问授权。

接收顺序：验证 task / scope→校验路径归属与访问权限→读取并核对实际 hash / schema→检查关键证据和缺失项→再供父模型汇总。父级不能把 partial 改写为完整通过。

### 22.2 Context 编译：每轮不是把所有东西拼起来

可以把应用准备模型输入的过程理解为“编译视图”，并非某个新框架：从可信任务契约、当前阶段、证据索引与可用技能中选出本轮必要内容。

建议明确四种区域：

- 可信约束：用户授权范围、系统政策、当前阶段；最终仍由代码强制。
- 已确认事实：有来源、时点和版本的结构化记录。
- 待核实材料：网页、搜索结果、工具文本，标明来源与不确定性。
- 临时推断：模型假设与下一步建议，不混入已确认事实。

自然语言分隔不能提供密码学安全，但能降低混淆；真正安全依赖实际能力和执行检查。不要让摘要器把待核实材料提升为可信约束。

### 22.3 压缩是否合格，看什么验收？

用相同原始任务做压缩前后比较，重点检查否定约束、金额单位、对象身份、有效期、失败 / 未知状态、证据回源路径是否保留。不是要求摘要逐字相同，而是后续决策不丢必要条件。

一个有效测试是：原文写“禁止导出；预算尚未确认”，摘要后如果变为“完成订单研究，准备发布”，即使语句更简洁也应失败。权限约束还需在工具层继续成立，不能把摘要完整性作为唯一安全控制。

### 22.4 写入工具返回成功，父任务为什么仍可能读到半份报告？

**先给结论：** Backend 提供的文件读写能力不应被当成跨文件事务或完整发布协议。具体原子性由 Backend、底层存储和应用操作决定；不能因为函数叫 `write_file`，就推断正文、索引和 manifest 一起提交。

典型时序是“正文更新→manifest 更新→父级读取”。正文成功、manifest 失败，会留下孤立工件；先发布 manifest、正文尚未完整，就会出现引用可见但内容不可用。两个子 Agent 复用同一报告路径，还可能互相覆盖。

应用可按需要采用以下最小发布契约；这是通用设计，不是 0.7.15 自动提供的默认机制：

1. 每个 task / attempt 使用独立工作路径，禁止用共享的 `latest-report` 当所有子任务输出位置。
2. 先生成完整内容并按业务 schema 验收，再记录确切内容版本、长度和完整性摘要。受控读取应核对实际读到的同一份内容，不只检查路径存在。
3. 验收后才发布指向不可变内容的引用或完成标记。若要切换“当前版本”，需要存储支持的原子更新 / 条件写；对象存储不能想当然套用本地 rename 语义。
4. 父级只消费已发布、scope 匹配且通过自身验收的版本。写完正文不等于父任务业务成功，partial 也不应被包装成 complete。
5. attempt 已失效或任务已取消时，旧 worker 不得再覆盖新结果；由可信发布层检查当前任务版本，不能只让模型口头承诺不再写入。

**连续追问一：能让模型最后写一个 `done.txt` 吗？** 只能作为候选完成信号。若模型可任意写标记而应用不验正文、scope 与版本，仍能发布不合格内容。

**连续追问二：正文和 manifest 都有 hash，就没有竞争了吗？** Hash 能发现内容不匹配，不能让两次写入原子化，也不能阻止过期 worker 替换“当前引用”。完整性、发布一致性与权限是三类保证。

**验证方式：** 分别在正文写入前、中、后，manifest 发布前、后注入失败；增加重复交付、两个 attempt 并发和取消后迟到提交。断言父级不读取未发布内容、不把旧结果当新结果，并保留可追踪的失败状态。这里描述回归设计，本次没有执行存储操作或故障测试。

## 23. Skill 与委派的评估：从“加载成功”到“确实有帮助”

### 23.1 技能发现、选中、执行是三个阶段

| 阶段 | 典型故障 | 可以检查的信号 |
| --- | --- | --- |
| 发现 | 路径错误、缓存旧索引、同名覆盖 | 实际 metadata、来源、版本 |
| 选择 | description 太泛，所有任务都触发 | 应选未选、不该选却选、混淆类别 |
| 执行 | 正文不可操作、工具不存在、完成标准空泛 | 是否调用必要能力、证据是否齐全 |

加载成功只证明第一阶段某部分有效。模型读完整正文后也可能执行错；如果根本没加载，应先排查发现和选择，不必直接重写十页正文。

### 23.2 如何做技能消融实验？

在相同任务集上比较：无 Skill、短方法提示、完整 Skill、Skill＋子任务。固定模型、授权范围和验收，统计任务质量、非法动作、调用量、读取与委派成本。这样能看出收益来自方法内容、工具改进还是上下文隔离，而不是把所有提升都归功于 SKILL.md。

描述优化与正文优化使用开发集，保留混淆任务验证泛化；加入“不应触发技能”的负例。只看技能覆盖的正例会低估误触发。

### 23.3 面试时如何收束这部分？

可以回答：“我先把 Skill 当可版本化的方法包，验证发现、选择和执行；子任务用明确工件协议回传，父级只接收符合 scope 的证据；上下文压缩测端到端收益，不只看 token 减少；资源与权限隔离另行验证。”

本篇负责 Harness 的具体机制；队列、预算与整体评估方案见 [Agent 实战演练](./05_agent_engineering.md#agent-practice)，不在每个文件里重复整套生产架构。
