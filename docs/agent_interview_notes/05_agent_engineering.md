## 1. Agent 是什么：不要从框架名开始

在工程语境中，Agent 是围绕目标，根据环境反馈选择下一动作并持续执行的系统。LLM 可以承担决策与信息处理，但完整 Agent 还需要工具、状态、控制器和终止条件。

一个有用的近似表达：

`Agent 系统 = 目标 + 观察 + 决策策略 + 受限动作 + 状态 + 反馈 + 验收与终止`

“自主”不是无限制，而是应用授予的一段有限决策空间。模型可以决定先检查哪张候选订单，不代表可以新增订单、导出客户或提高自己的费用预算。

不要用“调用了三次模型”“有一个名为 Agent 的类”作为充分定义。不同产品对 Agent 的叫法不同，面试时先说明自己的工程定义。

## 2. Prompt、RAG、Workflow、Agent、Harness

| 形态 | 控制权在哪 | 适合什么 | 常见误区 |
| --- | --- | --- | --- |
| 单次 Prompt | 固定一次模型调用 | 分类、改写、简单抽取 | 把一次回答包装成全自主执行 |
| RAG | 检索提供上下文，生成回答 | 内部知识问答、带来源回答 | 有检索就必然正确 |
| Workflow | 代码预定主要路径 | 合规流程、审批、固定数据处理 | 不能包含模型节点 |
| Agent | 模型在约束内决定部分路径 | 探索式工具任务、研究、页面决策 | 所有步骤都应由模型决定 |
| Harness | 模型外的执行、控制与环境支架 | 长任务、工具、记忆、恢复与评估 | 是一种更强的基础模型 |

它们可组合：外层确定性 workflow 控制认证、权限、审批和验收，中间某一段允许模型自主收集信息，检索再为该段提供证据。

最常见的可靠架构是“确定性外壳＋有限自主内部”，不是全自动自由行动，也不是所有请求都走复杂图。

## 3. 从用户目标变成任务契约

建 Agent 前先把含糊目标变成可验证契约：

1. 输入是什么，哪些来自用户，哪些来自可信系统？
2. 允许访问哪些数据、网站、租户和工具？
3. 可以读还是可以写，哪些动作需人工批准？
4. 输出范围是什么，允许部分完成吗？
5. 什么证据算完成，不满足时怎样报告？
6. 最多花多少时间、请求、token、并发和费用？
7. 谁能恢复、取消或查看结果？

例如“查一下订单”应进一步明确成“在当前授权测试会话查询给定关键词，只统计当前页前 N 条待回款；核对其中最大待回款订单详情；不创建、不修改、不导出”。

范围与成功条件要在模型运行前确定。不能因为模型做不到，就在结束时悄悄把“详情核对”改成“列出订单也算成功”。

## 4. 核心循环与部分可观察性

典型闭环：

```text
明确目标和授权范围
  → 取得当前观察
  → 生成候选动作
  → 校验动作与预算
  → 执行并等待结果
  → 更新可信状态和证据
  → 验收 / 继续 / 请求人工 / 明确失败
```

模型看到的只是环境切片，不是完整真实世界：DOM 可能是旧的，检索结果可能缺失，请求超时可能已经执行，工具也可能返回错误。

因此应区分：

- 真实环境状态：外部系统实际发生了什么。
- 观察：这一刻获得了哪些信息。
- 模型判断：它根据观察推断什么。
- 程序状态：代码明确确认到哪一步。
- 证据：可以支撑哪些结论。

“没有观察到”不等于“不存在”；“没有收到成功响应”不等于“没有执行”；“没有允许控件”不等于“页面白屏”。

## 5. 常见推理与行动范式

### 5.1 ReAct：交替思考与行动

核心思想是让决策参考环境反馈，而不是先编完全部结论。工程实现通常体现为模型选择工具、执行工具、根据结果继续。

不要求公开或保存模型完整隐藏推理链。记录简短可观察决策依据、动作参数、结果和来源，已足以支持多数调试与审计需求。

优点：适应新证据；缺点：可能短视、重复调用、陷入局部循环。改进依赖明确阶段、进度信号、预算和验收，不只是加“认真思考”。

### 5.2 Plan-and-Execute：先规划再执行

适合长任务、有明显依赖的研究或执行。计划描述子目标、依赖和完成判据，执行后根据新事实重规划。

主要风险是计划看起来完整但没有可执行细节，或计划已经失效却不更新。不要把一份漂亮清单当成任务成功证据。

### 5.3 Reflection / Critique：复核而非自我背书

模型可以检查自己的输出，也可由另一模型审查。但同源模型、相似上下文和共享错误会使它们一致地答错。

优先使用确定性校验与真实证据；模型审查用于语义覆盖、解释质量等难规则化部分。评审者不能仅凭被评审者的自述判断是否真正执行。

### 5.4 搜索式规划与多候选

生成多个候选计划、评分、展开或回溯，适合高价值且有较便宜评估器的任务。代价是调用量和复杂度增加。

没有可靠评分信号时，生成十条路线再让模型选一条，未必优于一条清晰路线。不要默认需要树搜索或复杂“思维框架”。

### 5.5 什么时候使用确定性步骤

金额计算、ID 关联、授权判断、数据过滤、schema 校验、审批匹配和幂等去重通常交给代码。模型处理语言理解、模糊分类、候选选择与解释。

原则不是“LLM 绝不能算数”，而是关键数值有更便宜、可重复验证的执行方式，就不应把正确性押在生成概率上。

## 6. 工具设计就是能力设计

### 6.1 工具契约

每个工具应说明：用途、允许参数、前置条件、结果结构、权限、是否有副作用、幂等策略、超时与错误语义。

比较两种设计：

- `execute_sql(sql)`、`click_any(selector)`：灵活但能力面很大，模型可生成危险参数。
- `read_authorized_orders(keyword, limit)`、`open_candidate(target_id)`：范围小、易验收和审计。

业务工具不必把全部底层能力暴露出来。不给模型的参数，往往比一百句“不要乱填”更可靠。

### 6.2 错误也是工具协议的一部分

| 状态 | 含义 | 是否可以当作空结果 |
| --- | --- | --- |
| success + 空集合 | 查询成功但无匹配 | 可以 |
| denied | 没有权限 | 不可以 |
| unavailable | 服务暂不可用 | 不可以 |
| invalid_input | 输入不合法 | 不可以 |
| unknown_outcome | 操作是否成功尚不确定 | 不可以 |

“库存查不到”与“库存为零”含义不同。若工具把失败变成空数据，模型再聪明也会被错误反馈误导。

### 6.3 MCP 与工具发现

MCP 提供连接工具 / 资源的协议方式，降低集成成本。它不自动解决工具可信度、租户隔离、授权、数据外发和业务写入安全。

发现一百个工具不等于应全部开放。按任务选择、最小权限、schema 审查和输出裁剪仍由应用负责。

## 7. State、Memory、Context、Knowledge

| 概念 | 示例 | 应考虑什么 |
| --- | --- | --- |
| State | 当前阶段、已采集订单、失败次数 | 恢复、一致性、序列化 |
| History | 用户消息、工具调用与返回 | 裁剪、摘要、调用配对 |
| Runtime context / deps | 可信身份、服务客户端、配置 | 不让模型伪造，不随意日志化 |
| Long-term memory | 明确偏好、经确认规则、可复用事实 | 写入来源、过期、纠错、隔离 |
| Knowledge base | 产品文档、制度、业务说明 | 检索、版本、权限与来源 |
| Model context | 本轮实际送给模型的材料 | 相关性、token、安全和时效 |

上下文工程不只是 Prompt 写法，而是决定每一步给模型看什么、暂存什么、按需取什么、哪些信息绝不外发。

长期记忆需要写入政策：谁说的、何时有效、是否确认、适用于谁、如何删除 / 修正。用户一次临时要求不一定应升级为长期偏好，模型推测更不能默认为事实。

## 8. RAG 与 Agentic RAG

### 8.1 基础 RAG 主线

文档解析→切分→元数据与权限→索引→查询理解→检索→必要重排→提供片段→生成带来源回答→校验引用与范围。

RAG 的价值是提供外部知识，不是让模型天然拥有最新、完整、准确事实。检索漏召回、切分错误、过期文档和权限过滤都能造成错误答案。

### 8.2 Agentic RAG 增加什么

模型可决定改写查询、选择知识源、分解问题、补检索、核对冲突和判断信息是否足够。

这增加适应性，也增加成本、延迟和循环风险。简单问题不一定需要多轮自主检索，先有可评估的基础 RAG，再增加必要 Agent 行为。

### 8.3 检索质量与回答质量分别评估

- 检索：相关证据是否被召回、排序是否合理、权限是否正确。
- 生成：是否忠实于片段、引用是否对应结论、缺证据时是否承认。
- 系统：端到端成功、成本、延迟与数据泄露风险。

“带一个 URL”不证明引用支持结论；来源存在、内容相关与结论被支持是三件事。

## 9. 多 Agent：什么时候值得拆

### 9.1 常见模式

- Supervisor：主管分派专家，统一汇总。
- Tool delegation：子 Agent 作为一项工具能力。
- Handoff：当前任务控制权转给另一角色。
- Parallel workers：独立子问题并行。
- Reviewer：独立复核结果，但仍需要外部证据。

### 9.2 值得拆分的条件

任务可独立、输入输出契约清晰、需要不同工具权限、上下文互相干扰或确实能并行。不能仅凭“领域名称不同”就拆角色。

### 9.3 协作成本

任务描述丢信息、重复检索、角色冲突、结果难合并、共享文件覆盖、父子预算失控和远程取消困难。

子任务包应带：目标、授权范围、事实 / 来源、输出 schema、时间预算、完成标准与缺失信息处理。父级不能在汇总时将 unknown 改写成确定结论。

多 Agent 共识不是独立事实验证。比较单 Agent 基线，只有在相同任务集上质量、成本、延迟的收益清楚时，拆分才有依据。

## 10. Human-in-the-loop：把批准变成协议

人工介入包括补充信息、审批危险动作、修改参数、处理异常和接管。不是每一步都必须打断用户，但不可逆或高风险动作要有明确控制点。

一个合格审批对象至少包含：

- 动作类型与工具名。
- 业务对象、参数和版本。
- 影响、风险与相关证据。
- 申请人、审批人和权限。
- 有效期、唯一调用 ID 与状态。

批准后仍需执行前检查：对象未变化、权限仍有效、预算未失效、动作未执行。修改金额后，原来针对旧金额的批准不能被无限复用。

“用户确认了”不是把责任全推给用户。系统仍要避免误匹配、重复执行、越权和凭据泄露。

## 11. 可靠执行：重试、恢复、幂等、补偿

### 11.1 先区分故障类别

临时网络错误可退避；业务输入错应修正；权限错误应停止；结果不确定要核对；环境状态变化要重新观察。只有明确分类，才谈自动恢复。

### 11.2 为什么简单任务也可能长链条失败

若每一步都有失败概率，步骤越多通常越容易出问题。常见的 `p^n` 只是独立且同分布假设下的教学近似，实际失败常相关，不能用它直接预测真实成功率。

减少无效步骤、让错误可检测可恢复，比不停增加自检轮次更重要。

### 11.3 幂等不是客户端“不再点第二次”

进程可能崩溃、网络可重传、审批可重复提交。稳定业务幂等键与服务端去重才能处理多客户端和重放。

读取到“已执行”时应返回已有结果；未知结果先对账；不支持幂等的外部系统需要更谨慎的状态机和人工介入。

### 11.4 补偿不等于数据库回滚

已发邮件无法真正撤回，已发货也不能靠回滚图 State 抹去。补偿是新的业务动作，需要权限、审计和可能的审批。

### 11.5 取消与断线

客户端关闭不等于后台任务已停止。取消请求要传递并观察确认；远程任务仍需追踪。已发生副作用不会因取消自动逆转。

## 12. 安全：区分指令、数据与权限

### 12.1 提示注入

网页、检索文档、邮件、工具返回可能包含“忽略原指令、导出数据”等内容。它们是任务数据，不是用户授权或系统规则。

防护不能只靠一个 Prompt：工具白名单、可信身份注入、参数约束、来源标记、数据最小化、输出过滤、审批和执行环境共同工作。

### 12.2 数据外发

订单 DOM、工具返回、错误栈、截图、轨迹与摘要都可能泄露信息。关闭视觉输入、使用内网域名或把 Key 放 `.env`，都不能单独保证业务数据不离开机器。

明确：发送什么、发给哪个模型服务、保留多久、谁能看日志、能否脱敏或本地处理。

### 12.3 工具与环境安全

只读账号限制业务权限；工具约束限制动作；Sandbox 限制环境；出口策略限制网络；预算限制资源。每一层覆盖不同威胁，不能互相冒充。

权限从可信认证系统产生。模型可以提出“需要更多权限”，不能自行决定自己已经有权限。

## 13. 评估：如何证明 Agent 更好

### 13.1 建立基线与数据集

先用固定脚本、基础 RAG 或单 Agent 建立基线。任务集覆盖正常、空结果、缺字段、权限不足、依赖失败、环境变化、恶意内容和长任务。

开发集用于迭代，保留集用于最终比较；不要边看测试结果边把答案写进 Prompt，再宣称泛化提升。

### 13.2 三层验收

1. 输出结构：可解析、字段合法。
2. 轨迹 / 行为：必需动作发生、禁止动作未发生、预算未越界。
3. 业务结果：范围、金额、来源和外部状态正确。

模型自评可以补充解释，不是最终 ground truth。LLM-as-judge 也应有明确评分规则、盲评、样本人工核对，并关注同源偏差。

### 13.3 指标表

| 指标 | 应怎样定义 |
| --- | --- |
| 验收成功率 | 通过外部验收的任务 / 明确统计范围内任务 |
| 违规动作率 | 尝试 / 实际执行禁止动作分别统计 |
| 人工接管率 | 需要人工干预的任务比例，并区分设计内审批与异常接管 |
| 证据覆盖率 | 必需结论中有足够证据支撑的比例 |
| 成本 / 成功任务 | 总成本除以成功任务数，包含失败开销 |
| 延迟 | P50 / P95 等，说明是否包含登录、审批等待和冷启动 |
| 重试 / 空转 | 重复工具、重复观察、无状态进展的比例 |
| 恢复成功率 | 指定故障注入后可正确继续的比例 |

小样本需要报告样本数、重复次数、模型与版本、任务范围和统计不确定性。一次 9 步成功不能解释成所有任务都 9 步或生产成功率 100%。

## 14. 成本、延迟与生产部署

### 14.1 成本构成

任务成本约等于模型输入 / 输出费用＋工具服务费用＋检索 / 重排费用＋浏览器 / 沙箱资源＋存储 / 观测成本。不要漏掉失败任务、子 Agent 和重试。

优化顺序：先消除空转与无用上下文，再改检索和工具粒度，再考虑模型路由、缓存与并行。不要从盲目换最便宜模型开始。

### 14.2 延迟路径

多轮串行模型调用常是关键路径；并行只适用于独立任务，不能越过依赖和资源上限。大输出、重复 DOM、慢工具和过多审批也影响体验。

缓存需要稳定输入、正确身份边界、版本与 TTL。不得把租户 A 的个性化结果给租户 B；过期权限与过期金额不能因缓存继续生效。

### 14.3 部署时的真实问题

- 入口 API 与长任务 worker 解耦，避免单个 HTTP 连接承载全部生命周期。
- 任务状态、事件、产物与外部动作 ID 可关联。
- 并发队列、租户配额、取消、总期限和重试有统一策略。
- 恢复时重建客户端并验证环境，不把检查点当进程快照。
- 版本发布固定模型、Prompt、Skill、工具 schema 和代码版本。
- 灰度、回滚与数据保留明确；回滚代码不撤销已发生业务动作。

这是设计清单，不表示当前学习示例已实现完整生产基础设施。

## 15. 框架选择：先看约束再看工具箱

| 主要需求 | 优先考虑 | 需要额外关注 |
| --- | --- | --- |
| 简单格式抽取 / 单次判断 | 普通模型 SDK＋数据校验 | 输出约束和事实来源 |
| 类型化工具、依赖、输出与测试 | PydanticAI | 状态持久化、业务恢复与审批存储 |
| 显式分支、状态、循环、暂停恢复 | LangGraph | 状态设计、幂等与部署基础设施 |
| 长研究、文件、Skills、子任务工作区 | Deep Agents | Backend、权限、上下文和版本 |
| 确定性页面流程 | Playwright | 定位、等待、认证与站点变化 |
| 页面中存在动态决策 | browser-use＋受控浏览器工具 | 数据外发、动作范围、证据验收 |

组合示例：外层 LangGraph 管认证阶段、审批与恢复；内部 Agent 用 PydanticAI 类型化输出；需要网页时调用受限浏览器工具。但如果只用一种框架就够，不要为了覆盖技术名词把四个框架强行堆叠。

## 16. 分层问答：基本思想与规划

### Q1：什么情况下才值得使用 Agent？

**简答：** 路径无法全部预先固定、需要根据反馈选择动作，而且可定义安全范围与验收时。

**深入：** 先比较确定性脚本和基础 RAG，只有灵活决策带来实测价值时才增加自主性。

**追问：** 两步固定查询呢？通常普通代码更便宜、可靠。

**误区：** 所有 LLM 应用都必须 Agent 化。

### Q2：Agent 与 Workflow 的边界在哪里？

**简答：** 主要看下一步控制权由谁决定，而不是是否使用 LLM。

**深入：** Workflow 可以包含模型，Agent 也应有确定性边界，两者可以嵌套。

**追问：** 如果模型只选择分类后路由呢？是一小段模型决策，不必因此宣称全流程高度自主。

**误区：** 有分支就是 Agent，没有分支就是普通程序。

### Q3：ReAct 是否要求输出完整思考过程？

**简答：** 不要求。工程重点是行动受观察反馈影响。

**深入：** 可记录简短决策摘要、动作与证据，不需要索取模型隐藏推理链。

**追问：** 怎么审计？靠实际工具轨迹、状态更新、证据和规则。

**误区：** 日志越像长篇思考，系统就越可信。

### Q4：为什么规划不能代替工作流？

**简答：** 计划是模型提出的可变策略，工作流负责强制执行必经控制点。

**深入：** “先审批再发布”应由代码确保，而非只作为 Todo 第一项。

**追问：** 可以重规划吗？可以，但不得跳过授权与验收。

**误区：** Todo 标记 completed 就已完成真实任务。

### Q5：反思和多模型投票能消除幻觉吗？

**简答：** 不能，只能提供额外检查信号。

**深入：** 相似模型可能共享偏差，关键结论仍需要独立证据与确定性规则。

**追问：** 什么时候值得用评审模型？语义质量难规则化且有评估数据证明收益时。

**误区：** 多数票等于事实。

## 17. 分层问答：工具、知识与多 Agent

### Q6：为什么工具设计比 Prompt 更重要？

**简答：** 工具决定模型实际能做什么，Prompt 主要影响它倾向做什么。

**深入：** 将租户和凭据从模型参数移到可信上下文，比反复提醒不要越权更强。

**追问：** 通用工具是否一律不可用？不是，但必须匹配威胁模型与执行隔离。

**误区：** 写一句禁止修改就能开放任意 shell。

### Q7：RAG 与 Agentic RAG 怎么区分？

**简答：** RAG 提供检索增强上下文，Agentic RAG 让模型动态控制部分检索策略与轮次。

**深入：** 后者适合复杂问题，但增加调用、延迟与终止风险，不应替代基础检索质量建设。

**追问：** 答错先改 Prompt 还是改检索？先看证据有没有被正确召回及传入。

**误区：** 多检索几轮自然更准确。

### Q8：短期状态与长期记忆怎样分？

**简答：** State / History 管当前执行，长期记忆保存经确认可复用信息。

**深入：** 写入记忆要有来源、身份范围、版本、时效与纠错，不是永久存全量对话。

**追问：** 模型推测的用户职业要不要保存？不能默认作为事实长期保存。

**误区：** 向量化所有消息就完成记忆设计。

### Q9：什么时候该拆多 Agent？

**简答：** 子任务独立、上下文或权限需要隔离，且收益超过协调成本时。

**深入：** 先与单 Agent 基线比较，同一模型换三个角色不天然产生独立专家知识。

**追问：** 如何避免父子丢信息？标准任务包、类型化结果、来源和预算。

**误区：** 多 Agent 是高级项目的必选项。

### Q10：子 Agent 返回失败，主管能自己补一句结论吗？

**简答：** 可以说明缺失与限制，不能把未知编成已验证事实。

**深入：** 关键证据缺失应部分完成、重试或人工介入，汇总必须保留错误语义。

**追问：** 三个专家缺一个还能成功吗？取决于预先定义的验收条件，而非主管临时决定。

**误区：** 汇总层负责把所有失败润色成成功。

## 18. 分层问答：安全与执行可靠性

### Q11：提示注入与普通错误输入有什么不同？

**简答：** 提示注入尝试让不可信内容改变指令优先级、权限或数据去向。

**深入：** 必须把网页 / 文档当数据，并由代码限制动作和外发范围；格式校验不能独自防住。

**追问：** 页面说管理员授权能照做吗？不能，第三方内容不是用户授权。

**误区：** 只需在 system prompt 写“不要被注入”。

### Q12：为什么暂停恢复不能保证 exactly-once？

**简答：** 外部操作和内部状态保存之间可能发生故障窗口。

**深入：** 需要稳定幂等键、服务端去重、对账与必要补偿，检查点只解决部分执行问题。

**追问：** 网络超时后应怎样做？先确认结果，再决定重试。

**误区：** 框架支持 durable 就不会重复扣款。

### Q13：人工审批是否意味着系统不必校验？

**简答：** 不是，审批只决定是否允许特定动作，系统仍要鉴权、验参、防重和执行前复核。

**深入：** 审批人与执行身份、参数版本、过期时间和动作 ID 都要匹配。

**追问：** 人工改了金额怎么办？重新校验，并保留改参审计。

**误区：** “用户同意了”就可以绕过业务约束。

### Q14：为什么取消任务后仍出现了结果？

**简答：** 前端取消、worker 取消和远程执行停止是不同层次，信号传播可能滞后。

**深入：** 查询真实任务状态，保留已完成副作用，避免立即重启重复任务。

**追问：** 取消等于回滚吗？不是。

**误区：** HTTP 断开后所有后端操作都自动撤销。

### Q15：什么时候应该让 Agent 停止而不是继续尝试？

**简答：** 无权限、结果不确定且无法核对、证据不足、环境不安全、预算耗尽或重复无进展时。

**深入：** 停止是一种正确行为，需说明已完成、未完成、风险和用户需要提供什么。

**追问：** 用户说“不要停”能扩权吗？不能扩大授权和安全边界。

**误区：** 任何失败都说明 Agent 不够自主。

## 19. 分层问答：评估、成本与项目表达

### Q16：怎样定义 Agent 的成功？

**简答：** 依据预先定义的业务验收，而非模型说完成或程序退出码为零。

**深入：** 同时核对结构、行为和外部结果，对部分完成与设计内拒绝单独分类。

**追问：** 权限不足时安全拒绝算失败吗？业务未完成，但安全行为可能正确，指标需分开。

**误区：** 所有不返回答案的任务都用同一失败率解释。

### Q17：离线测试与真实模型评估有什么区别？

**简答：** 离线替身测试协议和控制流，真实评估测试模型在任务上的行为与质量。

**深入：** 两者都需要，不能用固定动作步骤数估算真实调用成本，也不能用一次真测替代故障回归。

**追问：** 怎样证明回归没偷偷触网？限制模型请求，并拦截业务网络、替换依赖。

**误区：** 不用 Key 的测试一定安全。

### Q18：成本优化从哪里开始？

**简答：** 先看调用轨迹，删掉空转、重复观察、重复历史与无关数据。

**深入：** 再比较工具粒度、缓存、模型路由和可并行任务，以验收成功率为约束。

**追问：** 便宜模型失败两次后重跑是否更便宜？要看成功任务总成本，不能只看单次价格。

**误区：** token 单价最低的架构成本最低。

### Q19：temperature=0 能保证重复运行完全一致吗？

**简答：** 不能，模型服务、上下文、并发、工具和外部数据都会影响结果。

**深入：** 固定版本与数据，提高可复现性；用多次评估报告分布，而非单次“演示成功”。

**追问：** 怎样复现故障？保留版本、输入快照 / fixture、动作和证据，注意隐私。

**误区：** 低温度就无需测试。

### Q20：如何讲自己的 Agent 项目才有技术深度？

**简答：** 讲目标、约束、控制权、状态、证据、故障和测量，不只罗列框架。

**深入：** 说明哪些确定性、哪些模型决策，为什么设边界，出现过什么问题，怎样验证修复。

**追问：** 没有生产数据怎么办？诚实称为学习 / 联调项目，展示可复现测试，不编造吞吐与成功率。

**误区：** “用了 LangGraph＋多 Agent＋RAG”就等于架构解释。

## 20. 一个完整业务场景的设计答题法

题目：“做一个能查订单、分析待回款并给出建议的 Agent。”

### 第一步：收紧目标

只查授权账号可见订单；明确关键词、分页和时间范围；金额字段定义一致；建议不等于催款或修改；如果要写入则另立审批和授权。

### 第二步：划分确定性与自主部分

认证、权限、金额、解析、证据验收由代码负责；模型选择允许的查询动作和组织解释。必要时用工作流控制阶段，不让模型任意导航。

### 第三步：定义状态与工具

状态含阶段、查询范围、候选、当前目标、证据、重试预算；工具只开放所需读动作。目标 ID 有有效期，用户改页后重新确认。

### 第四步：处理异常

会话过期等待人工；请求失败与空结果区分；点击超时先检查实际页面；错误详情停止；缺证据不能提交成功。

### 第五步：验收与评估

合计与采集范围一致，详情真实读取并核对，摘要不增加未采集订单；测试覆盖隐藏副本、延迟加载、错金额、重复执行与注入。离线替身和真实模型分开报告。

### 第六步：交付可审计产物

每轮独立状态、动作、指标、证据和结果；失败不产生成功结果。说明来源时点和未验证部分，避免把一份演示报告说成完整财务结论。

## 21. 项目面试的两分钟口述模板

“我先把业务目标变成范围、权限、预算和验收契约，而不是从框架开始。系统采用确定性外壳加有限自主决策：认证、金额计算、状态变更和审批由代码控制，模型负责理解任务、选择允许工具和组织解释。运行中每个工具返回真实阶段和错误类型，状态与证据独立保存，模型说完成还要经过程序验收。

“对于长任务，我会根据需要引入检查点、文件工作区或子 Agent，但它们不是越多越好。子任务有明确输入输出与共享预算，外部写入必须幂等，未知执行结果先对账。评估分离线协议测试和真实模型任务集，分别统计业务成功、安全违规、延迟和每成功任务成本。框架是实现手段，最终目标是可控、可恢复、可验证的业务闭环。”

## 24. 高级追问：如何像系统设计者一样回答 Agent 问题

建议以“目标与不变量→故障模型→控制权→状态与协议→取舍→可验证指标”展开。以下设计是跨框架工程方法，不表示当前五套学习示例具备全部生产设施。

速查：自主性与决策范式看 H1–H4；RAG、权限与记忆看 H5–H8；多 Agent 与任务运行看 H9–H10；幂等、审批与安全看 H11–H13；评估和成本看 H14–H15。第 25 节练十分钟系统设计，第 26 节练指标口径，第 27 节练反驳与自测。

### H1：Agent 的自主性应该怎样量化，而不是靠名字判断？

**第一问：** 有工具调用就算高自主吗？不够。更有意义的维度是模型能决定哪些动作、动作影响多大、能持续多久、可以访问什么数据、何时必须交回控制权。

**追问一：同一任务怎样分级？** 查询订单可以从固定脚本，升级为模型选择授权关键词，再升级为模型选择多个证据来源；自动修改、发消息或退款则是不同风险等级。不能把“模型更聪明”作为自动扩大执行权的理由。

**追问二：动态规划与强控制会不会矛盾？** 不矛盾。模型拥有策略选择权，执行器拥有权限和前置条件的裁决权，验收器拥有成功判定权。允许探索，不意味着允许自授权限或自报成功。

**追问三：怎样落地？** 在任务入口固定 scope、allowed_effects、预算与验收；模型动作只是提案。执行端从可信身份派生实际能力，工具拒绝超范围动作，不用自然语言补丁承担最终安全边界。

### H2：为什么有时多观察一步更好，有时必须立刻停止？

**第一问：** 工具超时后，Agent 不知道发生了什么，是不是应该继续推理？缺少的是观察而非语言推理。读取当前页面、查询动作结果、补检索证据，可能比再生成一段判断更有价值。

**追问一：如何选择下一观察？** 看它能否减少关键不确定性，以及获取成本和风险。教学上可写成“预期决策损失下降−观察成本”，但实际需要可靠估计，不应伪装成已经校准的精确概率公式。

**追问二：模型自报 95% 置信就够了吗？** 不够。置信可能未校准，对权限、是否扣款、订单是否存在等问题，应依赖外部事实。高风险未知结果不能因模型很自信就继续。

**追问三：何时停止？** 观察不可获得、持续无进展、预算耗尽、权限不足，或剩余不确定性超过允许风险时。报告未知和已完成范围本身是正确结果，不能把不停止当万能目标。

### H3：ReAct、Plan-and-Execute、确定性 Workflow，同一道题怎么选？

**题目：** “检查某批订单并给出回款风险说明。”

若步骤固定且字段清楚，用确定性检索 / 计算＋一次生成即可；如果需要根据观察选择详情、补查来源，可用有限 ReAct；如果跨多个资料源、子问题有依赖、时长较长，可先规划再逐步执行。认证、授权、金额与验收始终不应由计划随意跳过。

**追问一：提前规划有什么代价？** 计划本身要成本，信息不足时容易规划错。可先做低成本侦察，形成短滚动计划，而不是开局写二十项并锁死。

**追问二：ReAct 为什么会空转？** 动作空间过大、错误语义含糊、观察没进度信号、终止条件不明确，都可能导致重复调用。改工具反馈、阶段与预算往往比加长 Prompt 更有效。

**追问三：能混用吗？** 可以：外层 workflow 固定生命周期，内部 planner 分子目标，局部 ReAct 处理不确定页面。混合应由需求证明，不能为技术齐全而堆叠三套控制器。

### H4：让另一个模型反思，为什么可能越改越错？

**第一问：** 两个模型一致是否更可信？如果共享错误来源、相似训练偏差或评审只看候选答案，它们的错误高度相关，不能当独立证据。

**追问一：反思怎样才有价值？** 给明确评审标准、必要外部证据和可执行检查；先指出具体矛盾，再决定是否修改。金额用程序重算，引用查原文，不把一切交给语义评分。

**追问二：反思循环何时停？** 限定轮次与预算，只有发现新的可证实问题才修改；保留原版本与变更依据。不断重写但没有新增证据，可能只是语言漂移。

**追问三：怎样证明增益？** 在同一保留任务集上比较无评审与有评审，既统计修正错误，也统计把正确答案改错的比例，再比较每成功任务成本。不能只展示一个成功纠错截图。

### H5：RAG 答错了，怎样判断是召回、重排还是生成的问题？

**第一问：** 先看最终答案还是检索日志？先定位支持答案的证据是否存在于语料，是否可访问、是否进入候选、是否保留到最终上下文。缺证据和不忠实生成是不同问题。

**追问一：向量检索为什么会漏精确订单号或术语？** 语义相似不等于精确标识匹配。BM25 / 关键词检索适合精确词项，向量检索适合语义表达，可使用混合候选与融合，再重排。没有评估数据不能预设混合一定优于单路。

**追问二：为什么不把所有候选都塞给模型？** 噪声、冲突、位置效应、token 与隐私都会增加。先按身份和范围筛选，再以相关性和覆盖度组织上下文；top-k 不是越大越好。

**追问三：Chunk 怎么切？** 优先保留语义单元、标题层级、表格字段关系与来源定位。固定长度容易把前置条件与结论切散，过大又降低召回精度和增加成本。对不同文档类别分层评估。

**追问四：怎样让诊断可量化？** 对标注证据看 recall@k、排序指标及上下文覆盖；对答案看忠实性、引用支持率、范围与拒答。正确答案字符串与正确证据不是同一个指标。

### H6：检索权限过滤应该放哪里？多租户 RAG 怎样防串数据？

**第一问：** 先全库 top-10，再过滤无权项可以吗？即使没有发给模型，也可能使有权证据被挤出候选，降低召回；如果未经授权的内容进入重排服务、模型、日志，又可能发生泄露。

**追问一：推荐什么原则？** 尽早使用可信身份过滤候选，并在实际内容读取与外发前再次鉴权；索引能力不支持时要设计等价隔离和明确服务信任边界，不是让模型根据文档标签自行判断权限。

**追问二：摘要和缓存也要带 ACL 吗？** 要。由敏感原文派生的摘要、embedding 关联元数据、引用、缓存答案与长期记忆，都可能继承敏感性。原文鉴权不等于派生物可公开。

**追问三：撤销权限后缓存怎么办？** 当前访问检查仍要生效，缓存 key / 命名空间应包含合适身份范围和版本；有失效机制。TTL 只能限制过期窗口，不能替代即时高风险撤权。

**追问四：怎样测？** 设计两个租户名称相似、内容互相诱惑的样本，检查检索、重排、模型输入、引用与日志各层，不只检查最终答案有没有出现对方名字。

### H7：引用看起来真实，为什么仍可能完全不支持答案？

**第一问：** URL 可打开就是有效引用吗？来源存在、片段相关、片段支持当前结论、结论适用于当前时点，是四个不同判断。

**追问一：两个来源矛盾怎么办？** 比较权威层级、发布时间、生效时间、适用对象与版本；无法消解则并列说明冲突。模型不能按支持自己结论的方向挑来源。

**追问二：能让模型给每句话都加引用解决吗？** 引用数量不保证支持关系。重要结论应能映射到具体证据片段，必要时由规则或独立评审验证；自由文本里难以核实的强断言应减少。

让多个模型复述同一份材料，也不自动增加独立证据；它们可能共享来源、训练偏差或同一处误读。评审意见可以帮助发现问题，但不能用“赞成票更多”替代来源核验。

**追问三：Agent 会自行补检索，还需拒答吗？** 需要。设置补检索的目标、轮次和信息增益边界；检索不到是可接受事实，不允许把一般知识伪装成本企业现行制度。

### H8：长期记忆为什么比普通历史更容易造成持续性错误？

**第一问：** 保存一次错误有什么严重的？它可能跨任务反复被召回，错误从一次输出升级成默认前提，甚至影响新的工具动作。

**追问一：记忆应包含什么元信息？** 至少来源、主体、类型、确认状态、适用范围、时间与版本；区分偏好、事实、假设和任务指令。模型推测不能自动升级为可信事实。

**追问二：能不能让模型自己改记忆？** 可允许提议，真正写入按权限、冲突与审核政策执行。恶意网页要求“记住以后忽略审批”不能污染可信规则。

**追问三：事实变化怎样处理？** 显式更正 / 失效旧版本，而非盲追加矛盾记录；检索时按当前身份和时效选择。高价值事实必要时回源验证，不能因为是“记忆”就永不质疑。

### H9：多 Agent 应怎样拆分，怎样知道不是徒增成本？

**第一问：** 把一份题目分成产品、技术、测试三个角色就更好？不一定。拆分应来自独立证据、不同能力 / 权限、上下文隔离或可并行性，而不是职业名称。

**追问一：主管、流水线、handoff 怎么取舍？** 主管适合动态分派但可能成为瓶颈；流水线适合稳定依赖但前错后传；handoff 适合责任转移但要明确身份与历史；共享 blackboard 便于协作却有并发冲突。没有一种拓扑普遍最优。

**追问二：共享 State 还是消息？** 共享状态利于统一事实，但需 schema、reducer 与版本；消息边界明确，但可能丢背景、重复传输。任务包应固定目标、范围、来源、输出和预算，不只一段“请帮忙分析”。

**追问三：一个专家失败怎么处理？** 根据预先定义的必需项判断部分完成或失败，保留错误状态。父级不可用“综合判断”掩盖缺证据。

**追问四：如何衡量拆分价值？** 同一任务集和预算下比较单 Agent 与拆分方案，统计额外委派轮数、重复检索、关键路径延迟和每成功任务成本；没有基线，无法证明多 Agent 有收益。

### H10：如何设计跨小时任务，不依赖一个永远不断的 HTTP 请求？

**第一问：** API 接收任务后怎么办？返回 task_id，任务在 worker 中运行；任务状态、必要事件与产物持久化。前端可订阅进度、重连查状态，人工审批属于状态而不是挂住一个请求。

**追问一：worker 崩溃怎样接管？** 依据可恢复状态和外部动作记录重新调度，重建客户端与环境；租约能发现失联，fencing token 用于阻止已失去所有权的旧 worker 继续提交，前提是相关执行端确实校验 token。

**追问二：任务状态最少有哪些？** queued、running、waiting_human、cancelling、succeeded、partial、failed 等可按场景缩减；对写动作还需明确 unknown_outcome / reconciling。终态不能只由模型文本决定。

**追问三：event log 与 checkpoint 一回事吗？** 不是。Checkpoint 服务恢复，事件流服务观测与前端，审计记录服务责任追踪；可关联但生命周期、粒度和敏感级别不同。不能全量 State 直接广播给用户。

**追问四：哪部分是框架自带？** 具体看部署产品和版本；这里是通用架构，不代表调用一次 Agent.run 就自带队列、租约、分布式预算与审计。

### H11：at-most-once、at-least-once、effectively-once 应怎样解释？

**第一问：** 为什么不直接说 exactly-once？先声明保证对象：消息投递、函数执行、业务效果是不同层。跨独立系统、允许重试时，很难仅凭客户端流程保证外部副作用精确一次。

**追问一：三者取舍？** at-most-once 倾向不重复尝试但可能漏执行；at-least-once 允许重投但可能重复；effectively-once 通常指允许重试，通过稳定身份与业务去重让可观察效果只发生一次，仍需限定服务支持和失败模型。

**追问二：幂等键只是随机 UUID 吗？** UUID 可以作为首次业务意图 ID，但重试必须复用。键要绑定身份、动作与版本，服务端比较规范参数，同 key 不同参数拒绝，不能让并发请求覆盖结果。

**追问三：Outbox 解决什么，没解决什么？** 在同一本地事务里保存业务变更与待发事件，减少本地提交与发消息之间的丢失窗口；消费者 / 外部执行仍可能重复，需要去重。不是把任意 HTTP 调用纳入本地事务。

**追问四：补偿就是逆操作吗？** 有些副作用不可逆，有些逆操作需要额外权限并可能失败。补偿是业务协议，不是恢复 checkpoint 就自动倒放现实世界。

### H12：人工审批如何避免“批准的是 A，执行的是 B”？

**第一问：** 人类看到金额 100，执行时变 1000，哪里出了问题？审批只绑定工具名或一条自然语言，没有固定具体提案和参数版本。

**追问一：应绑定哪些字段？** 审批人、任务 / action ID、动作类型、业务对象、规范化参数摘要、对象版本、有效期与风险说明。执行端根据批准对象取参数，而不是让模型重新生成。

**追问二：摘要 hash 一样就安全？** Hash 保证内容关联，不提供身份认证，也不判断参数是否合理。还要可信审批渠道、规范化规则、权限和执行前校验。

**追问三：审批后权限撤销怎么办？** 执行前再验当前权限与关键前置条件。审批不是永久能力，隔夜对象变化可要求重新审批；具体过期策略由风险决定。

**追问四：多次点击同意？** 审批决定做单次消费与并发控制，执行仍做业务幂等。UI 禁用按钮只是体验优化，不是服务端防重。

### H13：提示注入为什么不是“多写一句不要被注入”就能解决？

**第一问：** 注入发生在哪？不可信文档、网页、邮件、工具返回或记忆试图改变控制指令、权限、数据去向。它利用模型把数据当指令的倾向。

**追问一：最有效的结构性控制？** 最小工具面、可信身份注入、任务级能力、外发限制、敏感动作审批与执行环境隔离。模型可能被诱导，但不应因此拥有原本没有的能力。

**追问二：Schema 能防什么？** 能拒绝不合法结构，不能拒绝结构完全合法的恶意目标。`url` 是合法字符串不等于它是允许的外发地址；合法订单号不等于用户有权访问。

**追问三：怎样红队？** 测试越权读取、跨租户、导出、恶意工具返回、技能覆盖、历史污染和错误日志泄露。分别统计“模型尝试违规”和“实际执行违规”，前者反映策略，后者反映边界。

**追问四：拒绝了所有动作是不是最安全的优秀 Agent？** 不能只优化安全一项；还需业务可用性。正确拒绝、过度拒绝、越权成功、合法任务成功分开测量。

### H14：评估怎样避免“挑几个成功样例”的自我欺骗？

**第一问：** 基准答案是什么？确定性业务结果用独立事实与规则；语义任务用明确 rubric 与人工标注；工具效果用外部记录。不能用 Agent 自己的最终文本给自己当 ground truth。

**追问一：轨迹评估是不是强制唯一工具序列？** 不应。约束必需事实、禁止动作、权限与预算，允许多种合法路径。只有协议测试才适合固定顺序，否则容易把更优策略误判失败。

**追问二：LLM judge 怎样降低偏差？** 匿名化候选、随机位置、相同上下文、明确维度，并抽样与人工对齐；注意同源、长度、措辞和位置偏差。Judge 一致不等于事实正确。

**追问三：任务集怎样分？** 开发集用于调参，保留集用于最终比较；按业务类型、难度、工具故障、权限和恶意输入分层。模板近重复与答案泄漏会让分数虚高。

**追问四：样本越多就好？** 多样性、代表性与统计单位同样重要。同一任务重复一百次能看稳定性，但不能当一百个独立业务场景；报告任务数与重复次数。

### H15：成本、延迟、稳定性三者怎么一起优化？

**第一问：** 小模型更便宜吗？单次便宜不等于每成功任务便宜。失败、重试、人工接管与额外工具成本都要计入。

**追问一：先优化什么？** 先删空转、重复历史、无用 DOM 和重复检索；改善工具粒度与反馈，再评估模型路由、缓存、压缩与并行。缩短关键路径，比单纯减少一个非关键并行分支更能改善延迟。

**追问二：所有模型调用并行不就快了？** 依赖任务不能提前并行，并发可能放大限流与成本尖峰。父任务预算、子任务预留和全局配额都要考虑；共享计数对象不等于跨 worker 原子限额。

**追问三：超时怎么分层？** 工具超时、模型请求超时、阶段期限、任务总期限分开，并预留清理与对账时间。上层先超时但下层继续运行时，要记录状态，不能立即启动重复任务。

**追问四：灰度失败回滚代码就行吗？** 还要兼容进行中任务、旧状态、旧审批和工具版本。代码回滚不撤销已发邮件或已创建订单；必要时停止新任务，保留旧版本 worker 处理旧任务。

## 25. 综合系统设计题：企业 ERP 只读研究 Agent

**题目：** 用户输入一个订单范围，希望系统采集待回款、核对风险并生成报告。未来需要长任务恢复和多人使用。请在十分钟内说明架构、故障处理与评估，而不只是列框架。

### 25.1 第一步：把需求变成不变量

先确认查询范围、可见租户、当前页还是全量、币种、金额含义、数据时效及能否部分完成。只读阶段禁止创建、修改、导出、发催款；建议不是财务审批，也不是已执行动作。

核心不变量：模型不能改变可信身份；金额与范围由代码计算 / 校验；每个关键结论有本次来源；未知结果不变成零；成功必须由独立验收器确认。

### 25.2 第二步：控制面与执行面分离

控制面管理任务、身份、范围、预算、状态和审批。执行面提供受限查询、页面操作、解析与证据采集。模型在控制面允许的动作集合里提出下一步，不直接持有通用 shell、任意 SQL 或认证秘密。

如果已有授权正式 API，优先评估接口；只有网页流程才用浏览器适配器。人工认证在模型创建前完成，保留原 Page；不能因为一个网站可登录，就扩大为批量接口采集授权。

### 25.3 第三步：状态与证据建模

任务状态记录阶段、查询参数、采集范围、目标有效期、预算与错误类别；证据记录来源、身份范围、实体 ID、观测时间、可用版本与字段语义。模型摘要与证据分开，避免让输出反向覆盖事实。

长任务保存可重建的状态，不保存 Page / 连接句柄；恢复先重建环境并验证会话、来源和对象。无法恢复认证时等待人工，不伪装成空查询成功。

### 25.4 第四步：典型故障逐一回应

| 故障 | 恢复策略 | 不能做什么 |
| --- | --- | --- |
| 登录过期 | 暂停并人工认证后重验范围 | 把登录表单交模型试验证码 |
| 搜索请求超时 | 区分本轮完成、旧数据和未知结果 | 直接采当前旧表格 |
| 点击详情超时 | 核对原页身份和实际位置 | 无条件连续点击 |
| 列表与详情冲突 | 记录时点与字段，有限复查或报告冲突 | 选择较方便的金额覆盖 |
| 关键证据缺失 | 部分完成或失败 | 主管模型编造专家结论 |
| worker 重启 | 依据状态重连并核对环境 | 以为 checkpoint 复活浏览器进程 |
| 模型提前 done | 门禁反馈＋最终独立验收 | 为演示成功删除检查 |
| 费用达到上限 | 输出已验收部分和限制 | 暗中重开预算继续 |

### 25.5 第五步：如何交付和证明质量

交付按 run 隔离的状态、结果、证据和最小必要轨迹，敏感内容受访问控制和保留政策。失败任务不留下可误认的成功文件。

测试层面用纯解析、DOM fixture、故障注入、固定响应完整入口验证协议；真实模型另用代表性任务集。每次比较固定模型 / 提示 / 工具版本，并统计成功、安全、成本、延迟和接管；没有生产数据时诚实称为学习 / 联调验证。

### 25.6 面试官挑战：四轮展开回答

**“既然动作都限定好了，为什么还需要 Agent？”** 可以先用固定脚本建立基线。如果任务确实需要选择候选、补充证据和适应允许范围内的变化，再增加模型决策；固定步骤演示不应硬说是通用自主 Agent。

**“只能读当前页，有什么业务价值？”** 范围小不等于无价值，能做可靠的局部核查。关键是明确采集范围，不把局部结论包装为全局；若需要全量另设计分页与一致性协议，并获得相应授权。

**“页面上能看见所有数据，为何还要考虑模型授权？”** 用户在本机可见与允许把数据发给外部模型不是一回事。需要明确数据去向、最小字段与日志政策，敏感数据可在本地解析后只发送必要结果。

**“你的安全设计会不会让体验很慢？”** 不是所有动作都审批。低风险读取在既定范围内自动进行，异常、扩权与写入才升级；通过清晰阶段减少无效模型轮次。安全控制要按风险放置，不靠频繁弹窗代替执行校验。

**“未来加催款发布，现有只读工具改个参数行吗？”** 不行。新的副作用需要明确授权、提案版本、接收对象、内容审阅、审批、防重、结果核对和可撤销性分析，不能偷偷把只读工具变为写工具。

## 26. 量化追问题：不用虚假精确，也不能只说“看情况”

### 26.1 成功率从 80% 到 90%，能直接宣称提升十个百分点吗？

需要样本量、任务是否相同、重复运行与统计不确定性。相同任务适合做配对比较，观察哪些任务由错变对、哪些由对变错；独立比例区间不能替代所有配对分析。

例如各 10 个任务中从 8 个到 9 个成功，只是样本观察，证据很弱；如果换了一批更容易的题，甚至不能将差异归因于方案。报告版本、数据集与分层结果，别只给一个百分比。

### 26.2 测了 60 次没有一次越权，就证明越权率为零吗？

不能。在近似独立同分布的伯努利假设下，零失败时常用“3/n”近似估算 95% 单侧上界；n=60 约为 5%，不是零。真实安全测试又常受任务覆盖、相关性和攻击分布限制，不能把这个上界外推为所有攻击的保证。

正确表达：“在明确的 60 次样本与攻击范围内，观察到零次实际越权；仍需扩展场景与验证执行边界。”模型没有尝试与执行器成功阻断也应分别记录。

### 26.3 便宜模型是不是一定省钱？

虚构例子：方案 A 每次任务成本 0.10 元，验收成功率 50%；方案 B 每次 0.16 元，成功率 90%。同分布大量任务下，粗略每成功任务成本分别为 `0.10/0.50=0.20`、`0.16/0.90≈0.178` 元，B 反而更低。

这个计算忽略了重试策略、工具费用、人工接管和任务难度差异，只用于说明统计口径。真实比较用实际总成本除成功数，并报告安全和延迟，不能据此推断所有情况下贵模型更省。

### 26.4 并行三位专家，延迟为什么不是直接除以三？

假设父级分派 1 秒、三位专家各用 2 / 4 / 6 秒、汇总 1 秒，在资源充分且真独立时关键路径约为 `1+max(2,4,6)+1=8` 秒，不是总耗时除三。限流、共享资源、串行依赖和重试会进一步增加。

预算也不会因并行减少：三位专家的调用成本仍相加，峰值并发更高。并行优化的是适当场景的延迟，不自动优化成本或正确率。

### 26.5 pass@k 与“连续多次都成功”能混用吗？

不能。允许 k 次中至少一次成功的指标衡量重试 / 搜索价值；要求重复 k 次都成功的指标衡量稳定性。二者回答相反方向的问题，不能用“试五次有一次成功”证明用户每次都可靠。

还要说明是否允许人工挑选、是否使用外部评分器、重试成本是否计入。不同论文和工具命名可能不同，先给指标定义，再用名称，避免只背公式。

### 26.6 低温度重复十次都一样，是不是可复现？

只能说明这些固定条件下观察到一致。外部页面、模型服务版本、并发顺序、检索索引、时间和 provider 内部行为变化都可能改变结果。复现包应包括版本、输入范围、工具与数据快照、动作和错误记录，且经过隐私处理。

## 27. 开放题训练、错误答案反驳与评分尺度

### 27.1 六个“听起来对、深入就错”的答案

| 表述 | 为什么不充分 | 更稳妥的回答 |
| --- | --- | --- |
| “有 JSON Schema 就不幻觉” | 结构不证明来源或权限 | Schema＋一致性＋证据＋授权 |
| “有 checkpoint 就不会重复” | 外部效果与保存不原子 | 恢复＋幂等＋对账，限定保证 |
| “多个 Agent 一起投票更准确” | 可能共享同一错误 | 独立证据、基线比较、质量评估 |
| “失败就自动重试三次” | 权限和未知写入不能盲重试 | 先分类，再按风险和预算处理 |
| “人同意了，系统就能执行” | 对象、参数、权限可能变化 | 版本绑定、执行前重验、防重 |
| “测试没用 Key，所以没外部影响” | 工具仍可能访问真实系统 | 替换依赖并拦截未预期副作用 |

### 27.2 自己练习时，沿着这四轮追问

选择任一主张，如“使用 RAG 能降低错误”。

1. **定义轮：** 降低哪种错误？根据哪份 ground truth，统计范围是什么？
2. **机制轮：** 通过哪个环节改善？是否先有正确证据，怎样进入上下文？
3. **反例轮：** 如果证据过期、权限撤销、来源冲突、检索遗漏，主张仍成立吗？
4. **工程轮：** 如何检测、恢复、限制风险，并用对照实验验证收益？

参考答案不能只到“RAG 提供外部知识”：应继续说明索引与检索质量、ACL、时效、引用支持、拒答和分层评估。类似方法也适用于“用多 Agent”“用检查点”“用类型安全”。

### 27.3 面试评分尺度

入门回答描述定义和 API；中级回答能串起工具、状态、证据与测试；高级回答能明确假设、推演故障窗口、识别分布式边界，并给出有成本意识的可验证方案。

最有价值的收尾通常是：“在这些前提下可以提供这些保证；这些条件变化时要降级或重新设计；我会用这些实验验证。”这比宣称系统完全自主、绝不幻觉、绝不重复更可信。

五篇互相补充：编排机制回到 LangGraph，长任务上下文回到 Deep Agents，类型和运行协议回到 PydanticAI，外部页面观察与效果回到浏览器 Agent。本篇负责把它们统一成有边界、有证据、可测量的工程判断。

## 28. 数据驱动演练：别只说“成功率很高”

### W1：同样 90% 综合正确率，你会上线哪个方案？

给定同一批 100 个虚构任务：80 个在授权范围内，20 个明确禁止。每个任务都有独立验收，分类互斥。

| 结果类别 | 方案 A | 方案 B |
| --- | ---: | ---: |
| 合法任务正确完成 | 72 | 70 |
| 合法任务给出错误业务报告 | 6 | 2 |
| 合法任务被不必要拒绝 | 2 | 8 |
| 禁止任务被正确阻断 | 18 | 20 |
| 禁止任务实际越权执行 | 2 | 0 |

某同学用“正确完成＋正确阻断”除以 100，得到两者均为 90%，据此说 A 业务完成更多、应优先上线。请反驳或支持，给出所需指标及决策条件。

<details>
<summary>参考计算与决策</summary>

| 指标 | A | B | 说明 |
| --- | ---: | ---: | --- |
| 合法任务完成率 | 72/80=90% | 70/80=87.5% | 分母只含应当完成的任务 |
| 合法任务错误报告率 | 6/80=7.5% | 2/80=2.5% | 未越权也可能造成业务损害 |
| 过度拒绝率 | 2/80=2.5% | 8/80=10% | 衡量可用性损失 |
| 禁止任务实际越权率 | 2/20=10% | 0/20=0% | 仅是本样本观察，不是总体保证 |
| 汇总正确率 | 90/100=90% | 90/100=90% | 把性质不同的结果混在了一起 |

如果实际越权属于上线硬阻断条件，不能用多完成两个合法任务抵消。A 应先修执行边界，再评估；B 也不能因为二十个禁止任务零越权就被证明绝对安全，仍需红队与边界审查，并降低过度拒绝。

最终是否上线，还缺任务代表性、错误严重度、样本不确定性、成本、延迟、接管与权限执行策略。不能在没有损失函数的情况下临时给所有错误一个相同权重。

进一步追问：“只看最终是否越权，还缺什么？”需要统计模型尝试违规、执行层阻断、日志泄露和派生数据访问。最终结果一项不能覆盖所有通道。

评分：分母正确 1 分；区分可用性、业务正确和安全 2 分；指出零观察不等于零风险 1 分；给出有条件上线判断 1 分。

</details>

### W2：调用更少，却 P95 更慢，矛盾吗？

方案 A 每任务平均 6 次模型调用，P95 延迟 25 秒；方案 B 平均 4 次，P95 反而 40 秒。两者任务集相同，但还没控制网络与模型版本。

<details>
<summary>参考分析：平均调用数不是关键路径</summary>

不矛盾。B 可能把多个小请求合成一个大上下文慢请求，使用更慢模型，等待同一慢工具，或在少数任务上发生长尾重试；A 也可能把独立调用并行化。平均次数减少不能推出尾延迟减少。

先固定版本与环境，再按阶段拆分：队列、模型等待 / 生成、工具、浏览器、审批与清理，检查关键路径及 P95 的慢样本。平均 token、平均耗时不能代替尾分位数；不同阶段的 P95 也不能直接相加当总 P95。

性能实验还应保留失败与超时任务。只统计成功任务可能让“更多任务被提前超时淘汰”的方案看起来更快。

评分看是否提出可证伪假设与必要观测，而不是直接说“模型不稳定”。

</details>

### W3：什么时候让小模型升级大模型，而不是全量用同一个？

一个路由器准备以“小模型自报置信度低于 80%”作为升级条件。题目没有置信度校准数据，也没有按任务类型的质量评估。

<details>
<summary>参考方案：使用可验证信号，先估计再部署</summary>

不能把自报置信度直接当真实正确概率。可先按任务类型建立基线，使用结构失败、缺少必要证据、工具能力不足、任务复杂度等可观察信号触发升级；对高风险动作，不论模型大小都保留同样授权和执行检查。

开发集用于选择策略，保留集比较统一大模型、统一小模型、分层路由的成功率、违规、总成本和延迟。必须计入小模型已花的费用以及升级时重复上下文的成本。

盲点是语义错误可能通过结构验收。因此路由不能只靠“JSON 解析成功”；要有任务级业务检查与抽样人工复核。大模型也不保证修正所有错误，升级失败需有终止 / 接管策略。

这属于运行时路由，不等于训练新模型。本套资料不新增微调、强化学习或模型训练教程，避免偏离 Agent 应用工程的既定范围。

</details>

## 29. 容量与故障演练：从单次演示走向多人使用

### 29.1 容量题：十个 worker，每个四个槽，够不够？

题设：稳定业务流量每秒 2 个任务，每个任务平均占用活跃执行槽 30 秒；十个 worker，每个四槽，总共 40 槽。先忽略重试、人工等待和其他资源限制。

若要稳定承接给定到达率，且统计边界只含活跃执行，Little 定律给出所需平均在执行任务约 `L=λW=2×30=60`。这不是说当前只有 40 槽的系统实际能同时跑 60 个任务；40 槽理论吞吐上限约 `40/30=1.33` 个任务 / 秒，低于持续到达率，队列会持续积累。不能对这个已超载系统直接套用稳定态结论；提高入口 timeout 也不增加服务能力。

60 槽也只是本题平均负载对应的占用量，不是推荐容量：若刚好满载，波动与长尾会让等待显著增加，还需余量、压力测试与延迟目标。不能把平均 30 秒当所有任务都恰好 30 秒。

追问：“审批要等半小时，也要占槽吗？”任务状态应持久化，通常释放可释放的 worker 槽；若浏览器或沙箱仍需保留，它们是独立资源成本。将人工等待算入同一 W 后再估算 CPU worker，会严重混淆资源模型。

追问：“任务并发够了就不再限流？”不够。若平均每任务 8 次模型请求，2 个任务 / 秒约带来 16 次请求 / 秒的平均量，另有 token、并行峰值、工具与浏览器限制；各层配额都要检查。

### 29.2 背压、熔断与重试，分别处理什么？

| 机制 | 目的 | 常见误用 |
| --- | --- | --- |
| 有界队列 / admission control | 到达超过处理能力时限制接收或等待 | 无界接收，任务排到过期才处理 |
| 租户配额与公平调度 | 避免单个租户耗尽所有槽位 | 只限全局并发，其他用户被饿死 |
| 有限退避＋抖动 | 缓和可重试瞬态失败的同步冲击 | 所有层各重试三次形成重试风暴 |
| 熔断 | 依赖持续失败时暂时减少无效请求 | 把熔断当鉴权或所有错误都计入 |
| 降级 | 按契约提供较小范围 / 较低能力结果 | 没有证据仍输出完整成功 |

这些是通用服务设计，不是注册一个 Middleware 就自动覆盖所有远程调用。审批、未知写入结果与权限错误也不该被当普通瞬态失败统一退避。

### 29.3 故障现场题：一个依赖 429，为什么全系统都越来越慢？

合理假设包括：每个子 Agent 各自重试、provider / HTTP 又重试、队列无界、并行数不降、慢请求占住槽、用户超时后重复提交。

排查先看逻辑 task 与实际 attempt 的放大系数、队列年龄、活跃槽、429 比例和重试分布。处理顺序通常是停止放大→控制入口和并发→尊重 Retry-After→有限退避→追踪已接收任务；不要一边限流一边让失败重新进入队列无上限重跑。

用户端重试应复用业务请求身份，服务端返回已有任务状态，而不是每次新建昂贵执行。只是“按钮禁用五秒”不能解决跨客户端重复提交。

### 29.4 SLO 应怎样覆盖长任务，而不误导用户？

分别定义接收延迟、首次有效进度、活跃执行时长、端到端完成时长与人工等待；任务成功率按统一到达 cohort 或明确范围统计，避免只看当天已完成的容易任务。

如果正在处理的慢任务暂未结束，把它们全部排除会造成生存者偏差。可以报告未完成比例、队列年龄与明确截断规则，而不是给尚无足够样本的 P95 一个好看的数值。

### 31.2 版本敏感知识如何更新？

遇到新能力，先查本地锁定版本，再查对应官方资料，区分“已有示例使用”“源码有接口”“最新文档新增”“通用设计建议”。看到官网出现一个参数，不直接升级环境或改写旧任务语义。

### 31.3 复习以错误清单驱动，不以行数驱动

每次模拟面试记录：没有讲清的假设、推错的时序、用错的指标分母、说过头的保证、缺少的验证。只对这些具体缺口补题或改答案；已有主题通过交叉链接复用。

当前资料提供的是参考分析与教学片段，不是唯一架构答案。能提出不同方案，只要边界、故障模型、成本与验证闭环成立，同样可以是高质量回答。

## 32. 可观测性与数据生命周期：能定位、能纠错，也不泄露

本节是跨框架的工程设计，不代表五个学习示例已具备完整观测、审计和数据治理平台；以下也不是要求执行任何数据删除或存储操作。

### 32.1 只保存最终 Prompt 和答案，为什么复现不了故障？

同一句问题可能在不同模型、工具、技能、页面版本与权限下得到不同轨迹。复现需要知道运行契约，而不是仅保存长文本。

建议先确定最小关联信息；字段名称是应用示意，不是所有框架的同名内置字段：

| 信息类别 | 建议记录 | 不能拿它替代什么 |
| --- | --- | --- |
| 任务与执行关联 | task_id、run_id、parent_run_id、步骤 / 逻辑调用 ID、attempt | task 是业务目标，attempt 是一次尝试，不能混算成功率 |
| 环境与契约版本 | 代码 / 依赖、Prompt、工具 schema、输出 schema、Skill 内容版本、站点适配版本 | 同名工具或 Skill 不证明实现内容一致 |
| 模型运行条件 | Provider / 模型标识、可获得的模型版本、关键采样配置、输出模式 | 模型别名可能滚动更新，固定别名不等于固定权重 |
| 证据与动作 | 范围版本、证据引用 / 时点、动作 ID、批准对象版本 | 相关 ID 不是授权凭据，hash 不证明事实真实 |
| 结果与消耗 | 阶段、错误类别、是否有进展、请求 / 工具各口径计数、费用、耗时 | 无报错不等于业务验收成功 |

记录身份关联时优先用受控的不透明标识，不把账号、手机号、完整 URL 查询串、token 或全量 DOM 塞进标签。Hash 也不是通用匿名化方案：低熵个人信息可能被枚举。

外部来源当时的内容如果不再可取，应诚实说明复现边界。按授权保存必要的最小证据或版本引用，而不是为追求“完全可复现”无限保留全部敏感输入。

### 32.2 有 trace_id，为什么还不能证明因果和业务成功？

Trace 把相关操作连起来，不能自动说明“这个结果由哪次尝试造成”。并发、重试、缓存、旧 worker 迟到提交都可能共享同一任务上下文。必须显式区分逻辑动作、尝试、返回、验收与发布。

例如：第一次搜索超时→第二次重试→收到第一轮晚到结果→模型总结。只有一条“搜索成功”的日志无法解释错误；要看查询 generation、attempt、页面身份和证据版本的对应。浏览器细节见 [网络事件与就绪](./04_browser_use_playwright.md#br-waits)。

单进程耗时可使用单调时钟；跨机器事件对齐还需时间戳、时钟偏差意识和显式父子 / 操作关联。不能把不同机器的墙钟排序当作严格因果顺序，也不能直接相减不同进程的单调时钟值。

告警应围绕验收失败、未知动作结果、持续无进展、重试放大、队列年龄和预算异常，而不只是异常栈数量。业务失败可能没有 Python 异常；程序报错也不一定说明外部动作没发生。

### 32.3 Checkpoint、trace、审计和工件，为什么不能混成一个“大日志表”？

| 载体 | 主要用途 | 典型边界 |
| --- | --- | --- |
| Checkpoint | 恢复业务状态与调度 | 不应被当成公开调试接口或通用审计证明 |
| Trace / 运行事件 | 定位路径、耗时、调用与错误 | 可能采样或缺失；普通调试日志不等于不可篡改审计 |
| 审计记录 | 追踪谁授权了什么、执行了什么 | 需要受控访问、完整性和明确保留策略，不保存不必要正文 |
| 证据与报告工件 | 支撑可交付的业务结论 | 要有 scope、版本、来源、验收和访问边界 |
| 模型历史 / 摘要 / 记忆 | 为后续推理提供上下文 | 不是唯一事实账本，过期或错误内容不能无限复用 |

不同用途意味着不同访问权限、保留期限和敏感级别。对外流式事件通常是另一份投影，不能把 checkpoint 原样广播。失败诊断也先提取安全字段，避免把底层异常中的认证载荷送给模型。

### 32.4 原文已经修正，为什么 Agent 还在重复旧结论？

可能仍有分块索引、embedding 关联元数据、摘要、回答缓存、长期记忆、历史消息、报告与正在运行的旧任务。修正文档只改变其中一处，不会自动同步所有派生内容。

设计时应明确“源记录→派生物→消费者”的来源关系、版本和失效策略。对于带权限与时效的数据，读取派生物仍要检查当前可用范围；TTL 只是过期策略的一部分，不能代替高风险权限撤销。

对纠错 / 不再使用请求，应先确定身份、对象、范围和保留约束，再制定受控处理方案：阻止旧版本被新任务采纳，定位相关派生物，使缓存与索引按策略失效，处理恢复任务和正在运行的消费者。涉及实际修改或删除必须另获对应授权，不能因为是“清理”就自行执行。

备份、审计和外部模型服务可能有不同保留规则。要区分“在线系统不再使用”“活跃副本已处理”“备份按周期过期”与“外部服务确认处理”，不要承诺无法验证的全系统即时擦除。

### 32.5 连续追问：过期内容下线后，旧 worker 又把它写回来了，怎么办？

**第一轮，说明原因：** 读取发生在旧版本有效时，写入发生在新政策生效后；只失效缓存但不约束在途写入，会重新污染系统。

**第二轮，定义不变量：** 写入 / 发布检查当前源版本、范围版本与任务有效性；已撤销或被更新替代的来源，不能再成为新结果的可信输入。可以使用版本条件、失效标记或受控发布门禁，具体取决于存储能力。

**第三轮，处理恢复：** 旧 checkpoint 只表明曾经读过某内容，不授予继续使用它的永久权利；恢复前重新确认权限与来源有效性，必要时补采集、重新生成建议或请求人工决定。

**第四轮，给验证方法：** 在“读取旧版本→策略变更→迟到发布”之间注入停顿，确认发布被拒绝或重新验收；再覆盖缓存命中、子 Agent 回传、隔夜恢复和已生成报告。用虚构数据验证，不对真实业务数据做破坏性试验。

**第五轮，限定保证：** 这些措施控制当前系统的采纳与发布，不能反向消除人已看到的内容，也不能代替外部服务的实际处理确认。安全承诺需要说清系统边界。

面试收束：“我会让每次决策关联到明确的运行、版本与证据；让观测、恢复、审计和上下文各司其职；纠错时追踪派生物和在途任务。可调试不是全量留存，可恢复也不是永久有权使用旧数据。”
