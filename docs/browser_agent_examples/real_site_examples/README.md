# 真实案例：LanERP 订单查询与待回款摘要

这是基于实际登录、搜索和详情页观察编写的业务演示，不是把本地商城换一个 URL。
目标站点是 [LanERP 测试环境订单页](https://dev2.lanerp.com/web/#/order)。
此目录与 `examples/`、`demo_site/` 平级，复用上一级的 `.venv`、依赖锁和模型配置。

本例完成一个小闭环：自动检查登录 → 必要时等待网页人工登录 → 输入订单关键词 → 读取当前页前 N 条 → 精确计算待回款合计 →
打开一张订单详情核对总金额 → 输出 JSON 和截图。它不创建订单、不回款、不开票、
不发货、不导出文件，也不直接请求业务 API 或连接数据库。

## 直接运行：一条命令完成整个流程

所有命令均在上一级目录执行，复用已经配置好的环境和 `.env`：

```powershell
cd D:\PythonProject\LearnOne\docs\browser_agent_examples

# 请把关键词换成允许查询的测试订单；先确认数据可以发送到 .env 中配置的模型服务。
uv run python real_site_examples/agent.py --keyword DD-261015 --limit 5 --allow-model-data --pause
```

**不再需要先执行 `login.py`。** 程序会依次完成：

1. 打开本机 Chromium，尝试恢复 `.artifacts/erp_auth.json`，检查订单页是否可访问。
2. 已登录就直接继续；没有状态或会话过期时，程序停留在登录页等待你操作。
3. 你在网页填写测试账号，自己点击“获取验证码”。**程序不会点击获取验证码，也不会发送或重发短信。**
4. 你收到验证码后，在网页填写并点击“登录”；程序不在终端收集验证码、不替你填写或提交登录表单。
5. 程序监听原标签页进入工作台或订单页，再在同一标签页确认订单搜索框；不会另开订单标签页或关闭登录页。确认认证输入框已从 DOM 卸载后，终端只询问是否保存/覆盖本机登录状态；不保存也能继续本次任务。
6. 认证通过后才创建模型与 Agent；Agent 逐步搜索、读取、选择订单、核对详情，最后验收并输出结果。

登录成功后不需要回终端按 Enter 通知程序，程序会自动检测业务路由并接续（仍保留保存状态的确认）。
仅仅隐藏登录表单不会触发下一步，避免登录请求尚未完成就切页；请始终在程序打开的原标签页完成登录。
人工登录最多等待 5 分钟，`Ctrl+C` 可取消；验证码输错时，可在网页自行修正后再点击登录。
超时、关闭登录页或未确认订单权限时停止，不创建模型。安全验证也由用户自行完成，程序不绕过。
有效登录态会跳过整个人工登录过程；仅点击获取按钮不能保证短信已送达，请留意站点提示。

账号可以通过 `--account 测试账号` 仅做预填，但会进入终端历史和进程参数，推荐省略并在网页填写。
`--headless` 仅用于复用有效登录态；需要人工登录时程序会立即提示去掉该参数重新运行，不在无窗口中空等。

认证由用户在网页完成，`auth.py` + Playwright 只检查会话、等待登录并验证订单页权限。
验证码不作为模型工具参数，也不向模型开放认证控件。Agent 自主选择的是认证之后的订单动作，而不是处理登录秘密。
本例不把账号、验证码、token 写进动作日志；登录态文件本身包含 cookies/localStorage，属于敏感凭据。
如果业务页面本身显示账号等信息，它仍可能随业务 DOM 进入模型，并非整站脱敏。

## 再看三个学习入口

| 阶段 | 入口 | 谁决定下一步 | 模型是否接触业务数据 |
| --- | --- | --- | --- |
| 01 仅认证 | `login.py` | 用户在网页获取验证码并登录，程序检测成功后接续 | 否，不创建模型 |
| 02 固定流程 | `run.py` | Python 决定动作顺序，核对待回款最多的一张详情 | 否 |
| 03 受限网页 Agent | `agent.py` | 模型观察控件，逐步选择输入、提交、读取、点击和详情核对 | 是，需显式启用 |

先跑通 02，再运行 03，更容易区分“页面适配有问题”与“模型规划或输出有问题”。
本例使用 browser-use + Pydantic，不是 PydanticAI；后者请看相邻课程。

## 01：可选，只演示认证接续

以下所有命令都在上一级目录执行：

```powershell
cd D:\PythonProject\LearnOne\docs\browser_agent_examples

# 已安装本项目环境时无需重装；首次准备参考上一级 README。
uv run python real_site_examples/login.py
```

此入口使用与 `run.py` / `agent.py` 相同的认证流程，但确认订单页可访问后就结束，不查询订单。
需要登录时，在网页填写账号、自行获取并输入验证码、点击登录；程序检测成功并确认订单页可访问后，终端仅询问是否保存状态。
已有有效状态时直接验证并结束，不重复询问、不自动改写原文件。

验证码只在网页输入，程序不通过终端、命令行、`.env` 或历史记录收集验证码。不要把对话里曾经提供的验证码当成永久验证码。

登录状态相当于凭据，包含 cookies/localStorage，不应提交 Git、上传或共享。
`.artifacts/` 已被上级 `.gitignore` 忽略，但“Git 忽略”不是加密或文件权限控制。
标准 `storage_state` 不保存 sessionStorage 或 SPA 内存状态。如果站点依赖这些状态，
保留原标签页可以让本次任务继续，但保存文件不保证下次启动免登录；届时仍需在网页手动登录。
账号退出或会话过期后，下一次启动自动进入认证接续；权限不足会停止，不自动改用密码登录。
状态文件损坏时保留原文件，重新登录并确认保存后才覆盖；恢复接口失败则提示备份后处理。
保存采用临时文件完成后替换，避免写到一半破坏旧文件；没有额外增加文件加密。

## 02：先跑确定性查询

```powershell
# 替换成测试环境中现存的订单编号片段；以下前缀曾用于实际页面核对。
uv run python real_site_examples/run.py --keyword DD-261015 --limit 5 --pause

# 已在有窗口模式登录并确认保存有效状态后，才可无窗口演示
uv run python real_site_examples/run.py --keyword DD-261015 --limit 5 --headless
```

固定脚本也会自动检查并接续登录，无需单独预登录。认证完成后，你会看到脚本填写搜索框并按 Enter、
读取列表、打开待回款最多的一张订单详情。
终端打印结构化结果，同时在 `.artifacts/erp_order_query/<run-id>/` 保存：

- `orders.png`：列表查询结果截图；有订单时另有 `detail.png`。
- `result.json`：订单、客户名称、金额、发货状态、详情核对来源和采集范围。
- `status.json`：本轮 `running/success/failed`，失败不会生成成功结果。
- `actions.json`、`metrics.json`：逐动作状态、耗时、失败次数和模型调用次数；固定脚本调用次数为零。

金额使用 `Decimal`，JSON 中用字符串表达，例如 `"1100.20"`。待回款合计直接累加页面
的“待回款金额”列，不用“订单总额减累计回款”推算，避免忽略退款等业务规则。

`--limit` 只能是 1–15。`matched_total` 是页面显示的匹配总数，`rendered_count` 是本页
可读行数，`orders` 是其中前 N 条。只统计 `orders`，不翻页、不声称覆盖全量。
关键词不存在时会返回空订单列表、零合计、不打开详情，仍属于有效查询结果。
测试数据会变，不以某个固定订单数量或真实金额作为验收标准。

## 03：让 Agent 逐步操作网页

当前版本已经把一次包办查询的业务工具拆开。Python 先完成本机认证、打开固定订单入口；随后由
browser-use 模型观察页面并选择动作，不调用固定脚本的 `query()` / `verify()` 串联流程。
两种模式完成同一任务、使用同一组底层动作与金额解析规则，方便对照。

复用上一级 `.env` 中的 `LLM_* / DEEPSEEK_* / OPENAI_*`，不需要在此目录另建 Key。
模型配置与费用规则见[主 README](../README.md#配置模型并运行-agent)。

此阶段会把页面 DOM 文本和工具结果发送到你配置的模型服务。即使 `use_vision=False`，
订单金额、客户名称以及详情页上可见的联系人等仍可能进入模型上下文；它不是脱敏模式。
请先确认测试数据允许发送给该服务。未加 `--allow-model-data` 时直接退出，不启动任务。

```powershell
# 仅在已经确认数据可发送到当前模型服务后执行。
uv run python real_site_examples/agent.py --keyword DD-261015 --limit 5 --allow-model-data --pause

# 已有有效登录态时，限制模型步数，不显示窗口
uv run python real_site_examples/agent.py --keyword DD-261015 --limit 5 --allow-model-data --headless --max-steps 16
```

Agent 实际只拥有以下动作：

| 动作 | 能力与边界 |
| --- | --- |
| `observe_page` | 读取当前允许操作的真实控件，返回本次 `target_id`、控件文字、输入值、页面阶段与 `next_action` |
| `input_text` | 对最近观察到的搜索框填写命令行指定关键词；不能换关键词或输入框 |
| `press_enter` | 在该搜索框提交并等待搜索完成；不能提交空搜索 |
| `read_orders` | 搜索完成后单独读取当前页前 N 条和精确合计，不自动打开详情 |
| `safe_click` | 点击最近观察到的候选订单；失败后确认真实页面位置，只允许原订单最多两次点击尝试，不自动读取金额 |
| `read_detail` | 读取实际打开的详情金额、交叉核对并记录来源 URL |
| `done` | 输出受 Pydantic 约束的摘要；声明成功时先检查真实查询与详情证据，不通过则返回错误让模型补齐或明确失败 |

一条可能的执行轨迹是：观察 → 填写 → 重新观察 → 按 Enter → 读列表 → 观察候选链接
→ 选择并点击订单 → 读详情 → 完成。实际模型可能增加观察或遇到失败，并不固定为这些步骤。

`target_id` 来自当前可见控件，例如 `o1:search`、`o3:order:2`；它不是任意 CSS、URL
或 browser-use 全页面 DOM 索引。重新观察、输入、提交和点击会作废旧目标，模型需要
使用新观察里的标识。未提交本轮搜索不能读列表；只打开详情、未读取金额也不能验收成功。

每个动作都会返回当前 `stage`、`next_action` 和说明。取得目标后直接执行推荐动作，避免连续观察
消耗步数；详情阶段没有可点击控件也不代表白屏，应继续 `read_detail`。

点击详情发生异常时，不再一直停留在 `opening_detail`：

- 若仍在本轮订单列表，返回 `read`；重新观察取得新目标，只能重试原订单一次，不能换另一张。
- 若路由和精确订单标题已确认目标详情打开，即使点击曾报告异常，也进入 `detail`，直接读取金额；此时仍没有核对证据。
- 若页面关闭、位置不明、打开了错误详情，或第二次点击仍失败，进入 `blocked`，不继续点击，也不能声明成功。

这不是自动绕过页面遮挡：仍使用正常 Playwright 点击，不使用 `force`、脚本事件或无限重试。
固定脚本共享相同安全检查，但不会自行安排第二次点击；上面的重新观察与重试由 Agent 按反馈选择。

通用 `click/input/navigate/evaluate`、文件读写等动作仍被移除，新建订单、回款、开票和
导出按钮不会获得目标标识。工具层检查目标类型、页面阶段、关键词和候选订单范围，
不只依赖“不要修改”的提示词。

这里展示的是**有站点适配与安全边界的网页动作 Agent**：模型负责观察、选择动作和订单，
Playwright 负责执行单个已允许动作。它不是能适应任意网站的通用浏览器 Agent；
可操作控件的定位规则仍由开发者审阅，不能仅凭模型看到一个按钮就放开它。

模型调用 `done(success=true)` 时，程序先验证：是否执行查询、是否完整列出采集订单、合计是否与
`Decimal` 计算值一致、是否真正核对了待回款最多的一张。模型说 `success` 不代表验收通过。
不通过时，该次 `done` 不结束任务；模型可继续补证据，无法完成则用 `success=false` 结束。
运行结束后还会独立验收一次。以终端“业务验收通过，结果已保存”以及本轮 `status.json` 的
`success` 为最终依据，不以框架某条绿色结束日志或模型自己的描述为准。
自由文本观察仍需人工审阅，不用它判断逾期、客户信用或催款优先级。

产物目录：`.artifacts/erp_order_agent/<run-id>/`，成功时包括 `result.json`、
`evidence.json`、`page.png`，另有 `history.json`、`conversation/`、`agent_files/` 和
`status.json`，新增 `actions.json` 与 `metrics.json`。失败保留可用轨迹、动作及指标，
不生成成功结果。它们可能含业务信息，演示或排查前先脱敏，不要提交或上传。

## 对照演示：同一任务，脚本与 Agent 有什么区别

先用同一关键词、同一 `--limit` 分别运行 02 和 03。记录两次终端打印的完整产物目录，
再执行以下本地比较；将示例中的目录名替换为本次真实目录名：

```powershell
uv run python real_site_examples/compare.py `
  ".artifacts/erp_order_query/替换为脚本本次运行ID" `
  ".artifacts/erp_order_agent/替换为Agent本次运行ID"
```

`compare.py` 只读取本机文件，不重新访问 ERP，也不请求模型。它拒绝失败运行或
关键词、limit 不同的任务，输出：

- `same_snapshot`：订单、金额、匹配总数和采集范围是否一致。
- `same_checked_orders`：是否核对相同订单；待回款并列时，核对不同订单也可能都正确。
- `elapsed_seconds`：成功运行从认证完成后开始，包含业务网页动作、Agent 初始化和结果验收；不包含浏览器启动、认证/验证码等待、`--pause` 与浏览器关闭时间。认证阶段失败的记录则是从本次启动到失败的耗时。
- `action_attempts`、`failed_actions`：网页适配器层动作尝试及失败次数；包含观察和读取，不等于鼠标点击数，不包含 `done`。
- `model_calls`：模型 `ainvoke` 调用次数，包含抛出异常的调用；不展开 SDK 内部 HTTP 重试，不代表 token 或费用。

`actions.json` 能看到具体填写、提交、点击与读取，以及被拒绝的操作；Agent 的
`history.json` / `conversation/` 还保留模型当步输出的目标与观察，结合 `evidence.json`
核查其选择依据。模型自己的解释不是事实证明，最终仍以真实动作与金额验收为准。

详情点击的 `actions.json` 记录还包含 `diagnostics`：点击前后或异常后的路由类别、来源是否一致、
标签页数量、原页索引、页面是否关闭、候选数量、可见候选数量和目标详情是否已打开；异常只记录类型。
这些新增诊断不记录完整 URL 查询参数、输入值、token 或整页 DOM，但其他轨迹仍可能包含业务信息。
若点击抛错但目标详情已确认打开，动作可标记成功，同时保留 `after_error` 诊断；这不代表金额已核对。

两次真实运行并不共享数据库快照。若有人中途修改订单，`same_snapshot=false` 应先查
数据变化，不能直接判定 Agent 出错。也不要用离线固定响应的耗时或调用次数估算真实模型表现。

## 代码为什么这样写

主要逻辑在 [erp.py](erp.py)：

1. 页面使用 vxe-table，订单编号在左固定表，其他字段在主表。按 `rowid` 合并行、
   按 `colid` 对齐表头；不按两个表的行序号盲拼，也不重复统计行副本。
2. 页面存在两个同名“订单总金额(元)”列。所有可读同名值必须一致；不一致就停止，
   让人确认业务含义，而不是悄悄覆盖其中一列。
3. 搜索后等待本次关键词对应的 UI 请求完成，再等网络空闲及加载遮罩消失，防止读取旧表格。
   这里只识别请求是否属于当前搜索，不读取接口返回数据，更不绕开 UI 调接口。
4. 详情通过精确订单编号点击打开，不硬编码内部 ID；点击绑定事件的 `.order_num` 容器，
   不点可能被单元格遮挡的内部 span，也不用 `force` 或脚本事件绕过遮挡检查。
   独立读取详情总金额并交叉核对。
5. 真实站使用独立的 `BrowserSession`，不修改前 01–05 节仅允许 localhost 的会话配置。
   域名限制和工具白名单不是网络防火墙，也不能取代服务端只读账号权限。
6. 同一个 `OrderReader` 提供小动作。固定脚本用 Python 固定顺序调用；Agent 只拿到小动作工具，
   不能调用一次包办查询或核对的快捷方法。两种入口复用 `reporting.py` 记录指标。
7. `auth.py` 在模型创建前完成认证，用 Playwright 的一次性 `set_storage_state()` 恢复状态，
   不注册导航时反复覆盖 token 的脚本；只等待用户在网页完成认证，不自动获取/填写验证码或点击登录。
   登录表单隐藏后仍等待已观察到的业务路由（`#/workBench` 或订单入口），在原标签页进入订单页，
   避免新标签页丢失 sessionStorage/SPA 内存状态；`OrderReader.open_list()` 已在目标 URL 时也不重复刷新。
   人工登录后先确认订单搜索框可见、认证输入框已卸载，再允许创建 Agent；不能靠隐藏输入框掩盖认证信息残留。
   人工登录未完成或超时时不会生成模型对话或业务截图。
   登录异常按等待登录、确认搜索框、检查输入残留等阶段给出安全提示，不直接判定账号无权限，
   也避免原始 `fill()` 调用日志把秘密写进失败状态。
8. 真实订单页全页出现了三个相同 placeholder 的搜索框，但只有一个可见。
   `auth.py` 和 `OrderReader` 共用 `ORDER_SEARCH_SELECTOR`，只定位 `#pane-order` 内可见的搜索框，
   不用全页 `get_by_placeholder()` 或 `.first()` 猜测目标。若订单区域存在多个可见匹配，仍保守失败。

### 验证边界与真实站联调步骤

- 已有依据：此前通过浏览器查看过真实站的登录、订单搜索、固定列表格和详情字段。
- 上轮真实页面验证：在用户手动登录后的同一会话上，确定性只读动作通过登录检查、`DD-261015` 搜索、当前页采集（当时匹配两条）及一张订单详情总金额核对；没有调用模型、直接请求业务 API 或执行业务写入。这不是完整 Agent 通过的证明。
- 用户随后提供的真实 Agent 日志：登录与搜索成功，但详情点击超时，模型未核对详情却声明成功，最终被程序验收拒绝；点击超时的底层原因尚未证实。
- 本轮离线验证：使用虚构页面与固定响应模型，检查点击异常恢复、有限重试、诊断记录、提前完成拦截及原有认证/查询回归；不访问真实 ERP、不加载真实凭据、不调用真实模型。
- 尚未验证：本轮修改后的真实模型端到端运行，以及真实站点击超时的具体成因。已有真实页面验证也不覆盖全新会话整段登录、重启后的真实状态复用或真实站是否依赖 sessionStorage。真实查询结果随测试数据变化，不固定验收两条订单。

继续做真实站联调仍需确认只读访问范围，验证码由用户自行在网页获取；先运行固定脚本完成人工登录接续，再在确认业务数据
可发送到当前模型服务后运行 Agent，最后比较同一任务产物。不能把真实网页动作通过或离线替身通过写成真实模型端到端已通过。

## 演示时常见问题

| 现象 | 处理 |
| --- | --- |
| 找不到 `erp_auth.json` 或登录态已过期 | 无需预先登录，在打开的网页里自行获取验证码并完成登录 |
| 验证码错误/过期或没有收到 | 程序仍在等待时可在网页自行修正或按站点提示重新获取，程序不会代点；超过 5 分钟则重新运行 |
| 提示人工登录不能使用 `--headless` | 去掉 `--headless`，有窗口完成人工登录并确认保存状态后再使用 |
| 提示需要交互终端 | 使用本机 PowerShell 确认是否保存状态；验证码只在网页输入，不要增加明文验证码参数 |
| 登录后又打开一个订单标签页 | 旧版认证代码会主动新开页，已改为原页接续；重新启动程序使用新代码，不要把另一个浏览器的登录当成本次会话 |
| 已登录但仍找不到订单搜索框 | 看终端停在哪一阶段，并确认原标签页是否进入工作台/订单页、是否仍在加载或返回登录页；再检查定位规则和账号权限，这个错误本身不能证明无权限 |
| 页面看得到搜索框，但提示定位失败 | 检查是否全页匹配到其他页签的同名隐藏框；两个入口已共用订单区域内可见控件的定位，不要改成随便选第一个 |
| 订单编号点击被单元格拦截 | 使用绑定事件的 `.order_num` 容器并精确匹配编号，不点内部文本 span；仍有遮挡时检查页面布局，不恢复强制点击 |
| 详情点击超时 | 查看本轮 `actions.json` 的点击前后 `diagnostics`；仍在列表时只允许同订单重试一次，页面位置不明或重试耗尽则停止，不能仅凭超时认定无权限或白屏 |
| 观察结果没有控件 | 看 `stage`、`next_action` 与 `last_click_error`；详情阶段应读取金额，`blocked` 应明确失败，不连续观察或虚构已核对 |
| 框架显示完成，但没有成功结果 | 以业务验收提示及本轮 `status.json` 为准；`done` 声明成功但缺少详情证据会被拒绝，最终失败只保留轨迹，不生成成功结果 |
| 保存状态后下次仍需登录 | 会话可能已过期，或站点依赖 storage_state 不保存的 sessionStorage/内存状态；仍在网页完成登录，不复制 token 绕过认证 |
| 搜索等待超时 | 确认该关键词确实通过 UI 发起搜索；若请求编码/加载方式改变，检查 `OrderReader.press_enter`，不要删除等待直接读旧行 |
| 网络空闲超时 | 页面新增轮询时需要改成该站明确的加载完成信号；本例保守失败，不用固定 sleep 伪装同步 |
| 同名金额不一致、缺少字段、编号格式变化 | 列配置或业务语义变了，先人工确认并更新适配器与虚构测试页 |
| 列表与详情金额不同 | 可能有人同时修改订单；本轮失败，重新查询，不自动覆盖事实 |
| 达到步数或模型输出不合规 | 查看本次轨迹；先确认 02 能跑通，再检查模型能力与提示 |
| 目标不存在、已过期或动作不匹配 | 让模型重新 `observe_page`，使用本次返回的目标；不要自行猜测标识或恢复通用点击 |

页面观察基于 2026-10-15 的测试环境。没有增加通用爬虫、跨页全量统计或写入业务功能；
需要更复杂任务时，先扩充经过审阅的业务工具和对应测试，而不是恢复任意点击权限。
